# Neversoft Multitool - AI Assistant Instructions

## Project Overview

.NET 10.0 application for extracting and converting assets from Neversoft game files (PS1, Dreamcast, Xbox, PC). Features WinUI 3 GUI (Windows) and cross-platform CLI. Ported from Python/PyQt6.

Supported formats:

- **PSX files**: Multi-purpose format containing textures + optional 3D mesh geometry. File naming conventions: `*_g.psx` = level geometry, `*_l.psx` = texture library (paired with `_g`), `*_o.psx` = level objects, no suffix = character/creature/item model. Textures: 4-bit/8-bit paletted (PS1), 16-bit PowerVR (twiddled, VQ, rectangle) — PS1, Dreamcast, Xbox. Meshes: → glTF (.glb) with vertex colors, normals, and texture references. **`_o.psx` object banks are placed layers**: the bank's object-table positions are authored world instances (same convention as DDM/PSX layout placement), and companion TRG PLATFORM nodes (subtype 0x192, model-checksum opcode 0x212F) only OVERLAY scripted re-instances — corpus-proven by `tools/diagnostics/psx_level_object_survey.py` (TRG checksums reference a fraction of every bank: final l2a2 4/63, l4a1 0/19; coincident node/bank positions match exactly). `Core/Formats/Mesh/Conversion/PsxLevelObjectPlacementResolver.cs` seeds every bank object at its stored position, then TRG nodes replace their coincident bank instance (they carry authored rotation) or append re-instances (revised 2026-07-20; v1.3.2's TRG-only model under-populated every level). **Cross-game level-object parity** (2026-07-24): the placement pipeline covers the whole PS1 lineage via `MeshCompanionResolver.TryResolvePsxLevelCompanions` — Spider-Man `*_g.psx`, THPS1/THPS2 bare-stem levels (recognized by a sibling `*_o.psx`+`*_t.trg`; their v2.0 TRG PLATFORM nodes are verified coincident with the bank at div 2.25, THPS1 24/30 & THPS2 12/17 refs at δ≈0), and Apocalypse chunked levels (`*_obj.psx`/`*obj.psx` bank attached to ONE primary — bare `<base>.psx` if present, else the first chunk `_1`/`_1a` — so a batch convert doesn't place the shared bank per chunk). All three families get the full bank + PLATFORM-overlay + POWERUP-pickup stack (Apocalypse's PLATFORM refs are mostly re-instances of authored BADDY/PLATFORM spawns rather than bank-coincident, but they stay in-bounds at the same div-2.25 node scale; the per-game `PsxLevelCompanions.ApplyTriggerOverlay` knob is retained to gate any build whose overlay later proves unfaithful). **TRG POWERUP pickups** (`PsxPowerupPlacementResolver`, 2026-07-23; THPS + Apocalypse added 2026-07-24): POWERUP nodes (type 5) carry a numeric `pickupType` the engine's `CPowerUp` ctor stores as `mType` and switches to an items.psx mesh (`InitItem("items")` then `Spool_GetModel(hash)`; `Trig_CreateObject` passes the node subtype straight in, so TRG pickupType == mType). Spider-Man uses `switch(mType-8)` (per-build tables RE'd from all three binaries, re-verified by `tools/diagnostics/spiderman_pickup_table_probe.py`); THPS1/THPS2 use `switch(mType)` (SKATE letters 4/5/6/10/15 + bonus/money 21-32) transcribed verbatim from the **matched THPS2 decomp** `POWERUP.cpp` — the letter/bonus hashes are byte-identical to THPS1's items.psx so one hash-keyed table serves both (medal types 0x664-0x666 spool from skmedals, not items, so are omitted); Apocalypse uses a jump table keyed by mType-1 (types 4/5/6/10 + grey-gear 14/15/16, 17=plus_one region), **signature-matched with no SYM** by locating the "items" string + the items.psx hash-load cluster in `apocalypse_final.exe` (`tools/diagnostics/psx_hash_load_scan.py`) and reading the ctor jump table at 0x800A11EC, then cross-checked against the TRG POWERUP census (176/281 placeable). The correct table is picked from the sibling items.psx mesh set (`SelectTable`: Spider-Man by `?`/panel signature, THPS by the 'S' letter 0x311D55D4, Apocalypse by its pickupType-4 model 0x350E968C; unknown → no table). Placed translation-only (POWERUP nodes carry no rotation) from items.psx, merged into one items geometry pass, working with or without an `_o` bank. **POWERUP is authoritative for pickups**: a bank object whose mesh a POWERUP node also places is suppressed as a duplicate (l1a1's bank "?" drops for its 3 POWERUP "?"); a bank pickup with no POWERUP node (only the demo level `lda1`'s "?") still renders from the items copy. The per-build pickup table is selected by the sibling items.psx mesh set (Feb 6-mesh / Apr-29 7-mesh / final 9-mesh; the census subset {8,11,14,15,16} is identical across builds). Required a TRG fix: `ParsePowerup` skips the node link list before reading position (POWERUP nodes with links previously got garbage coords). **Grounded pickups reseat onto the floor** (`PsxGroundSnap` + `PsxTerrainHeightField`, 2026-07-25): POWERUP nodes carry a grounded-check u16 (0 = grounded), and `CPowerUp` calls `Utils_GetGroundHeight` at spawn, so the authored Y is only a spawn seed — the engine relocates the pickup onto the terrain (unlike props, which do NOT snap). `TrgNode.GroundedCheck` is now captured; for a grounded POWERUP the placement is base-snapped onto the level's own render geometry (the surface the engine ray-casts — Spider-Man PS1 has no separate collision mesh; `M3dColij` runs against `ppModels`) via a downward "resting floor" query (`TryGetRestingFloor`, mirroring `Utils_GetGroundHeight(pos,0,8000)`; nearest floor at-or-below the base, bounded so a pickup over a hole stays put). The snap is **engine-exact origin−hover**: the pickup ORIGIN rests `mGroundY − mHoverHeight` above the floor, per the decompiled `CPowerUp` (Spider-Man final SLUS_008.75, disassembled via `tools/diagnostics/psx_disasm.py`): ctor @0x8001DCC4 sets **`mHoverHeight = 128`** (world units) and `DoPhysics` @0x8001EB20 does `mOrgPos.vy = mGroundY − (mHoverHeight << 12)`. Hover is per game (`HoverWorldUnitsForTable`): Spider-Man 128; **THPS and Apocalypse do NOT snap** — the matched THPS2 decomp's `CPowerUp::DoPhysics` writes `mOrgPos.vy = mGroundY − hover` only on the `mDropping` path (ctor `Flags & 4`); placed pickups render at authored TRG Y plus a wobble centered on it, and THPS items.psx models are origin-CENTERED, so the earlier origin-on-floor snap half-buried every SKATE letter (fixed 2026-07-28; the old "THPS 0 (matched decomp)" claim conflated `mHoverHeight=0` with "always snaps"). Converted to model space by the file's translation divisor (128/2.25 ≈ 56.9). l1a1's seven "?" pickups floated at inconsistent authored heights → six now rest exactly 56.9 model units above their floor (engine-identical), one over a gap is left alone. **Ock's spline claw**: retail ships sibling `claw.psx`; the Feb-2000 protos ship the claw mesh (hash 0xCAB96557) inside the boss arena bank `l8a4_o.psx` — `PsxSplineClawLocator` falls back to scanning sibling `*_o.psx` banks and repackages the mesh (local space, bank texture library) so tentacle tips get their claws in every build; the proto carries no tube-skin texture (vertex-shaded tube is authentic there). PSX animation slots are anonymous (8-byte entries, no names anywhere in the format — engine plays them by index from game code); the tool's `anim_N` labels are synthetic. **Colour-pulse static export** (tagged chunk 7, RGBs palette animation): pulses bake their evaluated pre-tick playhead into the palette for level `_g` files (env regions tick every frame — `M3d_PreprocessPulsingColours` is called unconditionally in the THPS2 proto decomp) and standalone prop/item files (items.psx/fire.psx serialize BLACK for pulsed entries — the pulse is the only colour source), and **`_o.psx` banks bake too** (corrected 2026-07-29, refuting the 2026-07-22 raw-palette rule): `M3d_RenderSetup` ticks `M3d_PreprocessPulsingColours` for BOTH env regions, the obj-bank region, AND the items region every frame with no per-model gate (THPS2 proto jals 0x80095740..70; Spider-Man final 0x80076228..58) — the l1a1 "?"'s in-game dark blue was mis-attributed to the bank copy (it is the ITEMS-region copy's own staggered-blue pulse; the bank duplicate never reaches output via POWERUP suppression + items substitution), while fire/star bank art serializes BLACK with the pulse as its only colour source (raw palettes rendered the What If bike's flames and l8a5's night stars black). Probe: `tools/diagnostics/psx_colour_pulse_probe.py`; GLB hue scan: `tools/diagnostics/glb_vertex_color_scan.py`. **items.psx bank substitution** (`PsxItemsBankSubstitution`, 2026-07-23): bank meshes sharing a name hash with a sibling items.psx model render from the items copy under an `items` node prefix — pickups/markers are engine entities bound to the spooled "items" region (spidey-decomp `Spidey_CIcon::InitItem("items")`, `mModel=5` = the in-world "?"), so the l1a1 "?" gets items.psx's vivid staggered-blue pulse instead of the bank duplicate's placeholder R→G→B cycler. TRG references models by name checksum and items by numeric pickupType only — never by filename. **Level props (MANIPOB nodes: chairs, plants, papers) are placed at their authored TRG-node position verbatim and NOT ground-snapped** — decomp-verified 2026-07-25: `CManipOb::SquirtPos` copies the node position straight into `mPos` (`spidey-decomp ob.cpp:298`, `<<12` into 20.12), and `M3d_Render` translates the model's item vertices by `mPos` alone with no object offset or pivot (`THPS2 M3D.cpp` RenderModel/RenderModelNonRotated), so our render is bit-faithful to the engine across both placement AND the vertex-draw path. The l1a3 chair (hash 0x44EF15C1) is a **complete 40-vertex cantilever frame chair** (8 base-frame verts at the mesh's lowest band) whose base is authored ~5 model units into the carpet — it reads as "sitting on the floor" in-game; the earlier "only two legs" note was a misread of that authored embedding, corrected 2026-07-25. Diagnostic method: compare decoded object base-Y vs the level `_g` floor via a downward query over the render mesh. **Format versions** (0x03, 0x04, 0x06) are unreliable — prototype builds may share a version ID but differ structurally. v6 ships in ALL FOUR next-gen ports, always MIXED with carried-over v4 (census 2026-07-27, `tools/diagnostics/psx_version_census.py`, mesh-bearing files only): Spider-Man DC proto 78 v6 + 30 v4 + 2 v3, Spider-Man PC 180 v6 + 69 v4 + 3 v3, THPS2 DC 73 v6 + 75 v4, THPS2X Xbox 121 v6 + 60 v4 — in the THPS2 ports the skater characters stay v4 while re-exported levels/skyboxes/vehicles/items are v6 (the earlier "THPS2 DC/2X ship v4" note sampled the character class only; THPS2 DC SKB1 renders correctly under v6 treatment). v6-swept 2026-07-10 at 317 GLBs / 0 validator errors (v6 widens UVs to plane-separated u16/i16 pairs in a fixed /512 space — empirical, pinned by the BLACKCAT.PSX fixture). **ABR blend export**: semi-transparent faces (bit6) carry a 2-bit blend rate in flags bits 7-8 (decomp-verified face_flag_semantics.md) baked per-rate into textures: 0 = average → hue-preserving 50% alpha (62.5% of the corpus), 1 = additive → luminance-to-alpha (24.7%), 2 = subtractive → black+brightness alpha (10.1%), 3 = quarter additive (2.7%); rate is part of the material cache key. Survey: `tools/diagnostics/psx_abr_survey.py`. ABR-0 textured bakes keep the PS1 CLUT runtime-marker semantics (STP texels blend, ordinary texels stay opaque, key texels stay holes); markerless 16-bit (DC/PC v6) CUTOUT textures — anything with genuinely transparent holes, hard 1555 OR antialiased 4444 graduated wire edges (SKPH's fences) — keep their authored alpha instead of the uniform 50% wash (DC hardware source-alpha-blends the authored values — the wash rendered chain-link fences far too transparently, THPS2-DC user report 2026-07-28); full-coverage art (glass, no holes) keeps the 50% bake. **Sky/background layers are CAMERA-LOCKED, not world-placed** (decomp-verified across all five PS1-era engines, 2026-07-28): TRG command 0xAB `BackgroundCreate` registers a bank model by checksum on `BackgroundList`, and `M3d_RenderBackground` draws it each frame with the camera's ROTATION ONLY — GTE translation registers explicitly zeroed (`M3dAsm_TransformAndOutcodeBackgroundVertices` @0x80098F8C) and SZ forced to the far OT bucket, unlit, fog disabled; the sky's bank object-table position is DEAD DATA (sksf parks its dome 6,350 units below the level; the BackgroundCreate rotation args are parsed but never stored in any shipped ctor). `PsxSkyDomeClassifier.Classify` joins the TRG's 0xAB checksums against the bank mesh hashes (298/302 corpus commands join; survey `tools/diagnostics/psx_sky_background_survey.py`; geometric footprint heuristic kept only as a TRG-less fallback), anchors the static GLB bake at the registering (RESTART) node — the camera's start — and captures TRG 0xCA `SetSkyColor` (R=arg0, G/B=arg1 hi/lo bytes) as the backdrop. Export: `sky__` mesh/node prefix + `PsxSkyRenderMetadata(SkyColor)` → GLB extras `neversoftSky`/`neversoftSkyColor`. The in-app viewer renders sky layers in a DEDICATED SCENE drawn first with the depth buffer cleared afterwards (a semi-transparent dome — l8a2 — would otherwise sort into the transparent pass and draw OVER the level), swaps them to UNLIT materials, re-centers the sky nodes every frame on the camera (fly/walk) or the orbit TARGET (orbit — locking to an exterior orbit camera dragged the sky away from the model), uses SetSkyColor as the sky-pass clear colour, and excludes sky from framing + the walk ground raycast; Blender files sky objects into a hideable NeversoftSky collection. Spider-Man levels stack 2-3 layers (dome + clouds + skyline); THPS2's Skate Heaven assembles 6 pieces around the camera — all layers lock identically. **Coplanar semi-transparent layer stacks** get ONE extra lift step for genuinely stacked layers (`FindSemiTransparentLayerSteps`: overlap decided PER FACE PAIR via in-plane AABB penetration — union-bounds grouping chained retail lda1_g's side-by-side sign panels into a 2+-unit floating pile; top layer = the sole wibble-animated one, else PS1 OT insertion order — bucket-prepend means earliest-inserted paints last). SKB2's reported water z-fight is NOT a stack: two ST tile sets patchwork over an OPAQUE base at the identical Y — resolved by the standard one-step lift + the viewer's log depth buffer. **Near-equal-footprint OPAQUE coplanar pairs** (baked light/shadow duplicates — skmar ships floor sections twice, day + shadowed texture on the identical plane, 4 such pairs per build) are detected by `ClassifyPair`'s equal-size branch and resolved by the same OT rule: the earliest-inserted face becomes the draw-order overlay. That branch requires **real shared area, measured exactly** (2026-07-30): both coplanar faces project to the plane's dominant axis pair and clip against each other (Sutherland-Hodgman; PSX quads are stored in STRIP order, so the perimeter walk is 0,1,3,2 — the raw order clips as a bowtie), and the intersection must cover ≥1% of the smaller face. AABB penetration alone flags diagonal faces that merely share an edge (on l2a1_g 296 same-texture pairs reach the branch and 266 have zero polygon intersection — the AABB-only rule flagged 319 faces there, 294-312 of them false), while the cheaper centroid-inside test silently drops PARTIAL overlaps where neither centroid lands inside its partner (THPS2 DC SKPH.PSX 5 real pairs up to 0.32 of the smaller face, THPS1 skmall.psx 2 more at 0.23 — those regions z-fought). Current counts: l2a1_g 82 overlays (75 small-decal + 7 near-equal), lda1_g 18, l7a2_g 538, SKPH 29, SKB2 1, skmall 47, skware 37, skmar 39 / DC SKMAR 102, l1a2 nodes +3 combined; triangles unchanged in every case. Pinned per file by `PsxCoplanarOverlayCensusTests`; census tool `PsxAnalyzer overlay-census <file>`. **A coplanar pair with ANY semi-transparent member gets no flag** — the semi-transparent member already lifts 0.25 geometrically, so a draw-order flag would double-resolve it. This diverges from the pre-2026-07-29 rule that tested only the SMALLER member (SKB2 23→1 flags, skware 34→37, skmar −9 per build, lda1_g −2), which is why the per-file counts above are pinned. Re-open with an independent oracle before changing the lift. Semi-trans lifts move along POSITION-AVERAGED directions built per FILE in authored-world space (per-face directions physically tore the all-ST webdome open at every shared edge, and a per-mesh map left horizontal cracks at webdome3/firedome's per-ring object boundaries), and meshes without per-vertex normals get 60°-thresholded position-welded normals (`PsxNormalWelder` — the SKBUL sky dome's 32 texture-band primitives each shaded as their own facet island). **Engine-lit faces** (`IsEngineLitFace`): RE'd properly 2026-08-02 against the matched THPS2 decomp plus byte-level signature matching, correcting the earlier "authored albedo × lit(N)" claim, which is WRONG. `M3d_Render` takes the dynamic path when `(pModel->Flags & 4) || (pItem->Flags & 0x80)` — and the PS1 loader ORs each face's word0 into `SModel.Flags`, so the model bit just means "any face is lit" and the real selection is PER FACE in ProcessPolys. It then calls `M3dAsm_GetDynamicLighting` over the model's NORMALS, which writes **0x00FFFFFF (white) into the GTE RGB register once, outside its loop**, and runs `NCCS` per normal. NCCS multiplies by that register, so with white it is a no-op: **the shaded colour is the light alone and the authored vertex colours are never read** for a lit face. The identical instruction sequence appears exactly once in all NINE PS1-era binaries (Apocalypse, THPS1 ×2, THPS2 ×2, Spider-Man ×2, SM2:EE ×3; Spider-Man final @0x8007BFE4), so it is engine-wide. The light is per-ITEM (`pItem->mpLight`), which is why no file-level signal can identify it: ordinary items get `M3d_DefaultLight` (OB.cpp:233), the skater gets `Skater_DefaultLight` (MECH.cpp:629), and the front end substitutes its own (PLAYERSELECT/CREATE). `M3d_DefaultLight` is byte-identical in THPS2 and Spider-Man (found at 0x800A6214 in spiderman_final without symbols) — a HEMISPHERE rig, dirs (0,+1,0)/(0,-1,0)/(0,0,+1) with colour rows R(1.000,0.5625,0.500) G(0.500,0.8125,0.500) B(0.125,1.000,0.500) and ambient 0.125; PS1 is Y-DOWN, so the cool row lights upward-facing surfaces. `Skater_DefaultLight` is mono grey (0.156/0.719/0.078, ambient 0.531) — these are the constants this codebase previously mislabelled as a "front-end preview light"; they are neither front-end nor a preview. `PsxEngineLight.Evaluate` reproduces one NCCS (`ambient + ColorMatrix × max(0, LightMatrix·N)`, clamped) and `BakeEngineLight` applies it per lit face corner, scaled 255/128 into the textured modulation domain because a fully lit textured surface DOUBLES the texel rather than landing on neutral. Scanner: `tools/diagnostics/psx_light_table_scan.py`; disassembly via `tools/diagnostics/psx_disasm.py`. **Scope**: dynamic lighting is a CHARACTER/PROP feature only — a corpus lit-census finds **zero** lit faces in any level geometry (`_g`) file, 117 of 3,113 across six `_o` banks, and 224,221 of 241,069 across 401 character/prop files. Levels are entirely pre-lit with authored vertex colours, which is why they render correctly with no rig at all. **The rig is NEVER inferred**: the file records which faces the engine lights but never which light (`mpLight` is assigned only by game code — `OB.cpp` item default, `MECH.cpp` skater, `PLAYERSELECT`/`CREATE` front end), and TRG node type 501 is a `CWobblyGlow` lamp effect, not a shading light (`CBody::DoLightingSetup` is an empty `jr $ra`). So `PsxEngineLight.Presets` exposes only the rigs the decomp NAMES — `item-default`, `skater`, `skater-mars` — selected by the caller via `mesh --psx-light <name>`; omitted, lit faces keep authored colours for the viewer to light. Spider-Man's rig set was traced 2026-08-03 with no symbols (`tools/diagnostics/psx_xref_scan.py`): the binary holds exactly TWO stores of a light into `mpLight` (offset 0x38) — the item ctor @0x80058D90 assigning `M3d_DefaultLight` (0x800A6214), and @0x80048214 assigning **0x80098F1C**, whose ctor (entry 0x80047DF8) is called from two sites each allocating a 0x1020-byte object, the game's largest entity — the structural analogue of THPS2's CBruce, hence the `spiderman-player` preset. The other two candidates (0x80098E00/E40) are referenced by NOTHING — no lui/lo pair, no pointer word — so they are dead data or scan artefacts and are deliberately not exposed. **Sprite vertices** (vertex type bit4, mesh Flags 0x100): stored X = anchor-vertex byte offset (÷8 = index), Y = axis-mate byte offset, Z = signed half-width — NOT positions. The engine expands them at transform time into camera-facing AXIAL billboards anchored on the world A→B axis (handler 0x8009950C, k=1.6 for vertical axes from the 512-wide pixel-aspect bake, byte-identical in all nine PS1-era exes); the face's own texture/UVs/colours apply verbatim, and the type-0 anchor pairs are referenced by no face. THPS2 trees and Spider-Man antenna masts are sprite meshes (skph 192, l2a1 24) whose crossarms/foliage live in the texture — reading the raw fields as coordinates produced the reported thin-sliver leaves. `PsxSpriteVertexResolver` bakes the static quad, `PsxAxialBillboardMetadata` → GLB extras `neversoftAxialBillboard`/`Axis`/`Anchor` drive the viewer's per-frame axis-constrained rotation and Blender's LOCKED_TRACK constraint (NeversoftBillboards collection). **bit7-invisible faces stay dropped**: cross-build byte-level disassembly (10/10 PS1-era binaries carry the identical unconditional loader XOR + renderer 0xC0 skip; `tools/diagnostics/psx_bit7_loader_scan.py`) plus TRG cross-reference proved the dropped whole meshes are COMMANDPOINT trigger volumes, GapPolyHit detectors, camera zones, and collision proxies — the trees/towers users see in-game are separate visible meshes the converter already renders (census: `tools/diagnostics/psx_bit7_census.py`; 2026-07-28) — with ONE runtime exception: a fully-invisible bank mesh placed by a TRG entity node renders in-game as a forced-semi-transparent apparition (item flag 0x800 ORs 0x40|ABR via the GlobalFaceFlags scratchpad mask) — `PsxMesh.InvisibleFaces` retains the class and `PsxGhostFaces` emits `__ghost` additive meshes at the entity placements behind **default-OFF** per-object visibility groups (l1a2's Watcher head 0xD7833D12 + l5a1 + l8a4). Default-off since 2026-08-02: the apparition is a transient runtime state, not scenery — l1a2's Watcher is placed by BADDY/PLATFORM node 100 whose entire script is `V_MODEL_CHECKSUM` / `C_WAIT_FOR_COLLISION` / `C_SEND_PULSE_TO_LINKS_B` / `C_DIE_QUIETLY`, i.e. a proximity trigger that removes itself on contact (user-verified: the level reads correctly with the group off and wrong with it on). The geometry still exports and one checkbox restores it. **"What If?" props** are PLATFORM nodes whose scripts gate `V_MODEL_CHECKSUM` behind `C_IF_WHAT_IF` (0x4117) — `PsxWhatIfContentGate` collects them into a default-OFF `"What If?" content` visibility group (l2a1's motorcycle et al.; enabling the checkbox restores them). **Anim export**: tween-compressed clips expand in CycleAnim loop mode by default (final interval blends toward frame 0, decomp-verified cycle_anim_wrap.md); `--one-shot` restores the RunAnim clamp. Engine timeline: Apocalypse (1998) → THPS1 (1999) → Spider-Man (2000) → THPS2 (2000) → SM2:EE (2001)
- **Spider-Man PC/DC v6 runtime specifics**: the PC loader derives mesh dynamic-lighting state by OR-ing native face flags and testing bit `0x0004` (`SpideyPC.exe` 0x0045377A-0x004537F2); dynamically lit meshes ignore serialized flat/RGBs colours and export neutral modulation so glTF lighting can shade their normals. Tag-6 UV animation uses widened face UVs in a fixed 512-coordinate space, ignores its legacy base-UV byte pair, and doubles only the scroll term (0x0047619F-0x00476259).
- **PVR textures**: Standalone Dreamcast GBIX+PVRT textures (ARGB1555, RGB565, ARGB4444; twiddled, VQ, rectangle)
- **RLE/BMR bitmaps**: Neversoft's custom RLE compression — RGBA5551 (PS1) and BMP-wrapped 24-bit RGB (Dreamcast). The `rle` CLI + Bitmap Converter tab also convert standard `.bmp`/`.tga` (via ImageSharp, alpha preserved — `Core/Formats/Rle/BitmapFile.cs` facade)
- **WAD+HED archives**: Paired archive/index format used in Apocalypse, THPS series
- **PKR3 archives**: Compressed archive format used in Spider-Man PC
- **PRE archives**: Simple flat archive format used in THPS1 (PS1), THPS2 (PS1, Dreamcast). LZSS-compressed PRE v3 (0xABCD0003) also ships as **`.prd` (German)** / **`.prf` (French)** / `.prg` localized variants (THUG2, 316 files) — byte-identical to `.pre`, routed through `CompressedPreArchive` (THUG source `gs_file.cpp:52-63`, `p_filesys.cpp:130-158`). Localized variants extract to a full-name dir (`anims.prd/`) via `ArchiveNaming.GetExtractionStem` so they don't merge with the same-stem `.pre`/`.prx` sibling.
- **DDX archives**: Xbox texture archives containing DDS files (THPS2X)
- **QTex ZIP bundles**: THAW PC/GC texture-SOURCE archives (`<tex>.tex.zip.wpc` / `.zip.ngc` under `models/**`, 1,337 files). STORE-only PKZip holding the material's original authoring art (little-endian TIFF/PNG incl. `_n`/`_s` normal/specular maps) + a `debug.log` of `texturetool` build lines (EOCD comment "Generated by QTex"). The central directory is malformed (garbage extra fields; some files duplicate CDHs with the CRC in the compressed-size slot), so strict CD-based readers reject the whole corpus (Python zipfile 0/1,337) — `QZipArchive` walks the clean LOCAL file headers from offset 0 instead. STORE + DEFLATE supported; inner names are art-source names (no platform suffixing). CLI: `archive <x>.zip.wpc`; routed through `unpack`.

- **PS2 MDL/SKIN meshes**: Native PS2 scene files (.mdl.ps2, .skin.ps2, .iskin.ps2) → glTF (.glb) with vertex colors, normals, UV coordinates, and material references. Version triples: THPS4 (3,4,1), THUG (5,6,1), THUG2 (6,6,1). 2,299 standard files across 3 games (574 THPS4, 812 THUG, 913 THUG2). THPS4 uses full float-precision vertices (40B non-skinned, 64B skinned). THUG/THUG2 non-skinned uses floats with packed sint16 normals (32B); skinned uses packed sint16 for positions/UVs/normals (28B). Triangle strips encoded via ADC bits per-vertex (0x8000 = strip restart). Packed normals: 2×sint16, nz=sqrt(1-nx²-ny²), Z sign from LSB of nx. Skinned position scale: SUB_INCH_PRECISION=16.0 (÷16). Skinned UV scale: ÷4096. Materials are single-pass (not multi-pass like cross-platform format). VC wibble has phase field in ALL versions (THUG source bug omits it). THUG2 shader_id is always 4 bytes (no conditional specular color). 739 THUG2 .skin.ps2 files with version (1,N,M) are pre-compiled VIF/DMA rendering chains (bones pre-baked, lighting pre-computed, UVs confirmed via numerical cross-reference); detected and gracefully skipped since matching .iskin.ps2 files provide higher-quality data. **THPS4 strip winding**: mesh-version-4 ADC tristrips carry no reliable winding (sub-strips mix CW/CCW; ~half the triangles disagreed with the authored float32 normals — cockatoo 192/400), so THPS4 triangles are oriented to agree with the stored vertex normals (`orientToStoredNormals`, MeshVersion ≤ 4 only; THUG/THUG2 output stays byte-identical). **Material alpha**: transparent-flagged materials de-escalate BLEND→MASK/OPAQUE like the geom path — dest-alpha blends (C=Ad) export OPAQUE or the real alpha test (glTF has no dest alpha; opaque bases write A=128 so Ad=1.0), and std-source-alpha blends with bimodal cutout textures or a DELIBERATELY programmed AREF (≥ 2) export MASK (fixes Crown.mdl depth-write z-fighting). **AREF ≤ 1 is the GS always-pass default, NOT a mask** — exporting it as a cutoff was the THAW-PS2 'corrupted textures' regression (884d018: 364 materials MASK@1/128 forced stubble/hair overlays opaque across 184 skins; fixed 2026-07-16, corpus-validated 0 harmful transitions vs v1.2.0 by `tools/diagnostics/thaw_ps2_texture_regression_check.py`); opaque-blend cutouts with graduated art at the default AREF export BLEND (restores the overlay content v1.2.x hid — the 'Muska lost his hair' class). Reference: THUG source (scene.cpp/mesh.cpp/material.cpp), validated via `tools/diagnostics/ps2_scene_trace.py`.
- **THAW PS2 .skin.ps2 meshes**: Pre-compiled VIF/DMA rendering chains for THAW PS2 (.skin.ps2) → glTF (.glb). Binary layout: 32B header (numObjects, totalMeshes1, totalMeshes2, dataSize, bsphere) + object table (8B×N: checksum+meshCount) + entry table (64B×M: materialChecksum, textureChecksum, gsAlpha, ownerObjectChecksum) + variable-length gap chunks + DMA/VIF rendering data. FLUSH+DIRECT VIF opcode pairs mark material/setup changes inside the chain (full dword validation: 0x10000000 or 0x11000000 to filter false positives from gap chunk data), not true mesh starts; the VIF preamble before the first FLUSH+DIRECT can contain real vertex batches for the first material and must be included. Per-setup VIF batches: STCYCL(CL=3,WL=1) interleaved mode with V3_16 positions (sint16/16.0), V3_8 normals (sint8/127.0), V4_16 (c0=U sint16/4096, c1=V sint16/4096, c2=bone_hi|output_addr, c3=duplicate_addr|bone_data). **Strip topology via c2[7:0] + c3[7:0] output buffer addresses**: Each vertex's c2[7:0] encodes its primary position in the VU1 GIF output buffer (decreasing by 3 per slot). c3[7:0] encodes a duplicate output position; when c3[7:0] != c2[7:0], the VU1 microprogram writes the vertex to BOTH positions, filling gap slots that would otherwise fragment the strip. Sorting all entries by output address descending reconstructs the output strip order. Gaps (diff != 3) indicate degenerate vertex insertions → sub-strip boundaries. Cross-reference against PC ground truth on `skater_lasek` improved to 83.4% precision, 70.6% recall, F1=76.5% after including preamble batches; the remaining misses are mostly cases where all PS2 vertices exist but the strip topology differs across c2 runs or batches. Adaptive per-batch edge-length filter removes cross-body artifacts (median max-edge² × 16 threshold, marks oversized triangles as strip restarts). 332/332 files, 209,368 triangles, 0 parse failures, 0 glTF errors. No .geom.ps2 files exist for THAW. Also handles THUG2 pre-compiled .skin.ps2 without .iskin.ps2 companions — but ONLY those whose entry tables are THAW-conformant: `IsThawPs2Skin` validates that every 64-byte entry's owner-object checksum (entry+44) is 0 or one of the object-table checksums (332/332 THAW accept, 746 THUG2 pre-compiled with incompatible layouts reject instead of replaying garbage; `tools/diagnostics/ps2_skin_header_probe.py`). Archive scans collect `.iskin.ps2` stems up front so pre-compiled `.skin.ps2` entries defer to their higher-quality companions in ALL scan modes (was directory-scan-only). CLI: routed via `mesh` (the standalone `ps2scene` command class exists but is no longer registered). **Textures**: the companion `.tex.ps2` scene-texture format IS implemented (`ThawSceneTexFile` — version-6 TEX0-metadata scan + CLUT/pixel decode, DMA-REF-verified 905/905 unique textures across 332/332 files) and joins on entry-table TextureChecksum (1,325/1,329 materials direct; the 4 misses are mat=0/tex=0 placeholders); a TEX0 (TBP,CBP) fallback join hardens entries whose checksum is absent from the companion (`ThawPs2SkinSetupMapping.AugmentTextureOverridesWithTex0Fallback`, corpus no-op on Sample). Diagnostics: `tools/diagnostics/thaw_ps2_vif_walk.py`, `tools/diagnostics/thaw_ps2_strip_decode.py`, `tools/diagnostics/thaw_ps2_skin_texture_match.py`, `tools/diagnostics/thaw_ps2_scene_tex_walk_check.py`.

Two generations, both routed transparently through `QbFile.Parse`. **THPS3-THUG2 (2001-2004)**: raw token stream (69 token types, no magic number/header). Two-pass parsing: pass 1 collects CHECKSUM_NAME pairs, pass 2 indexes top-level items (scripts: KEYWORD_SCRIPT...KEYWORD_ENDSCRIPT, globals: NAME EQUALS value ENDOFLINE). 2,361 files across 6 builds, 0 parse failures, 36,634 scripts, 1,241,153 globals, ~77% name resolution. Format reference: THUG source `Gel/Scripting/tokens.h` (token enum), `skiptoken.cpp` (token sizes), `parse.cpp` (ParseQB). **THAW sectioned QB (2005, `.qb.ps2`/`.qb.wpc`/`.qb.ngc` + `.sqb.*`, same family as Guitar Hero)**: 28-byte header (u32 0 + u32 fileSize + fixed 20-byte signature) + typed sections holding a value tree (int/float/string/pair/vector/QbKey/struct/array). Reference: Nanook/Queen-Bee `QueenBeeParser/Qb` (`Sample/queen-bee`); diagnostics: `tools/diagnostics/thaw_qb_probe.py`. - **VID1 video**: THAW GameCube movie container (`VID1`+`HEAD`/`VIDH` chunks, MPEG-4-derived codec ported from the GC binary) → MP4 via pure C# decode piped to ffmpeg. Header: 512×384 @ 29.97 fps (num 2997 / den 100 at VIDH+8+0x10). All 8 corpus files convert (8/8). **In-app playback** streams through `Vid1MediaSource`: a dedicated worker thread decodes ahead into a bounded frame queue and sample requests take deferrals when they outrun it (the old synchronous design froze on decode stalls and ended the stream on any mid-stream hiccup — "some don't play"); seeks reposition on the worker (forward = fast-forward decode, backward = restart — VID1 has no random access) with newer scrubs superseding older ones, and mid-stream decode failures hold the last good frame instead of ending playback. **Seeking is anchor-based** (`Vid1SeekAnchorIndex` + `Vid1ReferenceSnapshot`): reference-state snapshots (~1 MB: both plane sets + MB-state mirrors + state words — exactly the `Vid1Decoder.Reset` field set) are captured every N emissions with adaptive spacing (cap 40 anchors, stride doubles when full), seeks resume from max(current position, best anchor, nearest PreambleClass-0 intra frame) and fast-forward with plane-only decodes (no BGRA conversion); the held presentation frame's BGRA regenerates from the reference planes (the held frame is always the last promoted reference — B-frames never promote). Byte-identical to linear decode (`Vid1SeekTests`). **Startup is stutter-hardened** (2026-07-16): a fresh Start-at-0 no longer resets the already-warm decode queue (`Vid1StartupSeekPolicy.IsRedundantStartAtZero`, headlessly unit-tested), the Starting request holds a deferral until ~6 frames are queued (500 ms timeout so short/broken files still start; deliberately NOT `BufferTime` — pipeline-buffering uncompressed BGRA taxes every seek), and the first ~1 MB anchor capture waits until emission ordinal 90 (~3 s) instead of 30.

- **Unpack tab** (GUI + CLI): Recursive extraction of all game archives in a directory. Supports WAD, PRE, compressed PRE (PRE3/PRX/PRD/PRF/PRG), PKR, DDX, BON, PAK, QTex ZIP, CUT, and disc images (ISO/CUE/GDI/IMG+CCD — a disc extracts into `{stem}/`, then its WADs/PAKs recurse). ## glTF Validation

After converting meshes to .glb, **always validate the output** using the Khronos glTF validator. Download a release from <https://github.com/KhronosGroup/glTF-Validator/releases> and either drop the binary at `tools/gltf_validator_bin/gltf_validator.exe` (kept out of the repo via `.gitignore`) or invoke it from wherever it lives on your system.

```bash
# Validate a single file
tools/gltf_validator_bin/gltf_validator.exe <file.glb>

# Validate a directory (recursive)
tools/gltf_validator_bin/gltf_validator.exe <directory>

# JSON report to stdout (parse with Python for material/texture/mesh counts)
tools/gltf_validator_bin/gltf_validator.exe -o <file.glb>
```

Key things to check: 0 errors, 0 warnings. `UNUSED_OBJECT` infos on `TEXCOORD_0` indicate meshes with UV coordinates but no texture assigned to the material — expected for untextured geometry, but a bug if textures should be present.

For quick programmatic checks, parse the GLB JSON directly (first chunk after 12-byte header):
```python
import struct, json
with open('file.glb', 'rb') as f:
    f.read(12)  # skip magic/version/length
    clen, _ = struct.unpack('<II', f.read(8))
    d = json.loads(f.read(clen).decode().rstrip('\x00'))
    print(f"Materials: {len(d.get('materials',[]))}, Textures: {len(d.get('textures',[]))}")
```

### Archive filesystem (`Core/Formats/ArchiveFs/`)

Archives are read through `IArchiveFileSystem` — a read-only filesystem over any WAD/PRE/PRE3/PKR/PAK/DDX/BON/ZIP/CUT container: lazily-indexed entries (`FindByPath` full-path case-insensitive with `\`↔`/` normalized, `FindByName` legacy flat first-wins, `FindAllByName` for directory disambiguation), **thread-safe per-entry reads** (`RandomAccess` on one `SafeFileHandle` — no whole-file buffering, so >2 GB WADs like Project 8's 2.78 GB DATAP.WAD open fine; the old `File.ReadAllBytes` backend rejected them), and **`TryOpenNested`** for archives-inside-archives (.pre/.prx/.prd/.prf/.prg/.pkr/.pak/.apk entries open in place with weak-ref'd buffers; nested PAKs auto-pair with sibling `.pab` entries in the same parent; depth cap 4). Detection lives in ONE place, `Archives/ArchiveTypeDetector.cs` (folded from the five previously duplicated extension/classification switches); `ArchiveFileSystem.TryOpen(path)` is the factory; `ArchiveAssetBackend` is a thin compatibility shim over it and `ArchiveAssetSource`/`AssetSource` remain the per-entry seam the converters consume. The per-entry `IsCompressed` flag is OVERLOADED per type (PAK = "has .pab companion", THUG WAD = NO_WAD external reference) — `ArchiveEntryDecoder` scopes real decompression to CompressedPre/PKR/ZIP only. Both GUI scanners walk nested archives breadth-first and probe entries with `Parallel.ForEach` + `IProgress` (THPS3's level `.bsp`/`.skn` inside SKATE3.WAD's PREs list directly; the Texture tab folder scan no longer freezes the UI on 10k-file trees). Parity/2GB/nesting tests: `tests/.../Core/Formats/ArchiveFs/` (unit `[Fact]`s + `[CorpusFact]` sweeps).

**Cross-tree companions**: THPS4/THUG level `.geom.ps2` live under `Levels/<Stem>/` while their `.tex.ps2` dictionaries ship only inside the scene PRE at `pre/<Stem>Scn/Levels/<Stem>/` — `BuildTreeCompanionLocator` (opt-in via `MeshCompanionResolver.ReadTextureCompanion(searchBuildTree: true)`, enabled for the PS2 scene/geom call sites) resolves those by walking ≤4 ancestors to the build root on disk, or via `FindAllByName`/sibling `{stem}Scn.pre` nested opens for archive-backed sources. `AnimationDiscovery` similarly handles archive-backed characters (same-backend `Anims/` entries, preferring the character's stem-scoped subdir) and PSX characters' sibling animation-bank `.psx` files (anim-named + companion-library stems; previously manual Add-folder only).

## Analysis & Diagnostic Scripts

When writing analysis or diagnostic scripts (Python, shell, etc.), **always create them as reusable files in the `tools/` directory** rather than running inline code via the console. This ensures scripts are preserved, versioned, and can be re-run later. Use descriptive names and include usage comments at the top of each script.

## Deferred Items

### Not Game Formats / Not Archives

- **SCC**: Microsoft Visual SourceSafe `vssver.scc` version tracking files. Development artifacts accidentally shipped on disc. No game data.
- **BIN**: Generic file extension used for PS1 MIPS code overlays (game logic, menu screens), THPS2 data tables (cretex.bin, tricks.bin), and Dreamcast bootstrap executables. ~89% compiled machine code. Not suitable for asset extraction. See [spidey-decomp](https://github.com/krystalgamer/spidey-decomp) for Spider-Man module decompilation.
- **PAK raw data files**: 987 of 1,732 `.pak.ps2` files in THAW are raw data without entry tables (not extractable archives). Detected and gracefully skipped by `PakArchive.IsPakArchive()`.
- **PRK**: Custom park save data (8-20KB files named `custom1-20.prk`). Not archives.
- **PPV**: CLOSED — not Neversoft. The `.ppv`/`.zoo`/`.bfx` files under `WTC/SOUNDS` in `Spider-Man (2000-2-4, PSX - Prototype)` belong to Codemasters' TOCA World Touring Cars (the proto disc SCED_026.36 is a multi-game demo disc). No extraction work planned.

### In Progress (Not Yet Bug-Free)

- **Script Decompiler tab** (GUI): Unified tab (`App/Tabs/ScriptDecompilerTab.xaml`) handles both TRG trigger files and QB compiled scripts. TRG: file picker (.trg), node tree with type/position/command detail panels, JSON export. - **QBKey name resolution**: all `QbKeyNames*.txt` embedded resources (~424,800 hash→name mappings total) are loaded at startup into a `FrozenDictionary` (first-wins, main file has priority). Format: `name=0xHASH` per line. `QbKeyNames.txt` (18,523): discovered via `qbkey cross-ref` matching DDM plaintext names against PSX QBKey hashes across 104 THPS2X Xbox file pairs, plus archive filename scanning — coverage: **mesh hashes 81.9% (19,336/23,611)**. `QbKeyNames.ThawDbg.txt` (137,054): harvested from THAW's shipped debug archives (`dbg.pak.ps2`/`dbg.pak.wpc` `[Checksums]` sections) via `tools/utilities/harvest_thaw_dbg_names.py` — drives THAW script decompilation to 89-99% resolution. **`QbKeyNames.QbLocalNames.txt` (206,215) is the biggest single source**: inline `CHECKSUM_NAME` (token 0x2B) registrations harvested GLOBALLY from the THPS3/THPS4/THUG/THUG2 script corpus and validated by re-hash (`tools/utilities/harvest_qb_localnames.py`; census `tools/diagnostics/qb_localname_census.py`). The engine only ever used these file-locally (`QbFile.LocalNames`), so a name defined in one script did not resolve in another; aggregating the proven pairs gives those four games — which ship NO debug archives, unlike THAW/Project 8 — their primary cross-file resolution. THAW's own `CHECKSUM_NAME` pairs were stripped in retail (they don't re-hash), which is exactly why THAW needs the separate `dbg.pak`. `DiscNames`/`ScriptRefs`/`CutScenes`/`ThpgDbg` add proven pak-key/script-ref/cutscene/Project-8 names. Texture identifiers are build-tool-assigned IDs (not name hashes), so QbKey resolution does not apply to them — but THAW textures DO recover source-art names via a **separate** map, `Core/Formats/Texture/ThawTextureNames.cs` (+ `.txt`, 2,132 pairs): the compiled-texture checksum → original art name mined from the `debug.log` inside each QTex `.tex.zip` bundle (`tools/utilities/harvest_thaw_texture_names.py`). It is deliberately kept OUT of `QbKeyNames*.txt` — those checksums are opaque build ids, not CRC(name), so mixing them in would poison every proven-name harvest's `existing_hashes()` and the coverage metric. Consumed by `ThawTexFile`/`NgcTexFile` naming (`ThawTextureNames.TryResolve(checksum) ?? QbKey.TryResolve(checksum)`).
  - **Hash algorithm**: PS1/DC/Xbox-era Neversoft games use **case-sensitive** reflected CRC-32 (polynomial 0xEDB88320, init 0xFFFFFFFF, no final XOR, **no lowercasing**). This was confirmed by verifying DDM checksum fields match case-sensitive CRC-32 of mixed-case mesh names (e.g. `Itm_Bonus01`). `QbKey.Hash()` is case-sensitive; `QbKey.HashLower()` provides the THUG+ era lowercase variant. The `io_thps_scene` Blender addon documents the same split: `crc32b_from_string()` (no lowercase) for THPS1/2 vs `crc_from_string()` (lowercase) for THUG+.
  - **Texture identifiers (NOT name hashes)**: The PSX "texture name" array stores opaque identifiers used as keys in `TextureChecksumHashTable` (a 512-bucket hash table, decompiled from THPS2 proto). `ProcessNewPSX` reads each identifier, looks it up via `Spool_FindTextureEntry__FUi`, then **replaces the value in-place with a pointer** to the texture entry struct. Values include small numbers like `0x0000001E` (30) that cannot be CRC-32 of any string, ruling out name hashing. Same identifier appears across files with different texture dimensions (e.g. `0x3FB86DC4`: hawk2.PSX 32x64 vs hawk2b.PSX 32x32), proving they're not pixel-data checksums either. The `TexId` field in the per-texture header is actually a **palette hash** (passed to `Pal_FindPaletteEntry__FUi`), not a texture name. These are build-tool-assigned identifiers; name resolution is not applicable. See `psx_decompiled.c` in the WSL decomp project (below) for the full decompilation.
  - `qbkey cross-ref <ddm-dir> <psx-dir>` — cross-reference DDM vs PSX hashes. `--export path.txt` merges discovered + existing mappings. `--scan-archives <builds-path>` scans WAD/PRE/BON/PKR/DDX archive filenames and hashes them against PSX pools.
  - `qbkey import <names-file> [--psx-dir <path>]` — import candidate names from external sources (e.g. C pipeline output), hash with QBKey, check against PSX hashes, optionally export merged dictionary.
  - **Texture hash diagnostic**: `tools/utilities/texture_diagnostic.py` — Python diagnostic script for analyzing PSX texture/mesh hash populations and testing alternative hash algorithms. ### Not Yet Implemented

- **THUG2 pre-compiled .skin.ps2 without .iskin.ps2 (bare conversions)**: 1,713 THUG2 pre-compiled skins route through `ThawPs2SkinFile` when no `.iskin.ps2` is available and convert to near-zero geometry (0-50 tris) — their VIF layout differs from THAW's. The 746 with non-THAW-conformant entry tables now REJECT at detection (owner-checksum gate) instead of replaying garbage; scans prefer co-located `.iskin.ps2` everywhere, so the GUI rarely hits this. A real THUG2-pre-compiled VIF decoder would be needed for the remainder (found 2026-07-15 during the 2g texture audit).
- **THAW multi-pass texture-stage baking (Xbox/PC scenes)**: `ApplyXbxMaterial` exports pass 0 only; pass-k (k≥1) stage-blend overlays (BlendMode 5/6) are dropped — e.g. ped_boone_full's spider tattoo `Cut_MBF_Boone_Tat01` is referenced only as pass 1 of material 0x71894AA9 and never reaches the GLB. Fix = composite pass-k PNG over pass-0 by pass-k alpha and register under a synthetic checksum (same pattern as `Ps2GeomDestinationAlphaSynthesis` synthetic textures).
- **RW DFF / THPS3 animations**: No animation support yet. THPS3 likely uses RenderWare animation chunks or custom Neversoft formats. THPS4+ uses Neversoft SKA format (BonedAnim.cpp). Skinned DFF models currently export in bind pose (T-pose). SKA parsing itself works (rpHAnim variant, 928/929 parse) — the unresolved part is rotation/translation composition semantics (see `docs/thps3-ska-animation-correctness-handoff.md`).
