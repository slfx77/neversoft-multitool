# Neversoft Multitool - AI Assistant Instructions

## Project Overview

.NET 10.0 application for extracting and converting assets from Neversoft game files (PS1, Dreamcast, Xbox, PC). Features WinUI 3 GUI (Windows) and cross-platform CLI. Ported from Python/PyQt6.

Supported formats:

- **PSX files**: Multi-purpose format containing textures + optional 3D mesh geometry. File naming conventions: `*_g.psx` = level geometry, `*_l.psx` = texture library (paired with `_g`), `*_o.psx` = level objects, no suffix = character/creature/item model. Textures: 4-bit/8-bit paletted (PS1), 16-bit PowerVR (twiddled, VQ, rectangle) — PS1, Dreamcast, Xbox. Meshes: → glTF (.glb) with vertex colors, normals, and texture references. **`_o.psx` object banks are placed layers**: the bank's object-table positions are authored world instances (same convention as DDM/PSX layout placement), and companion TRG PLATFORM nodes (subtype 0x192, model-checksum opcode 0x212F) only OVERLAY scripted re-instances — corpus-proven by `tools/diagnostics/psx_level_object_survey.py` (TRG checksums reference a fraction of every bank: final l2a2 4/63, l4a1 0/19; coincident node/bank positions match exactly). `Core/Formats/Mesh/Conversion/PsxLevelObjectPlacementResolver.cs` seeds every bank object at its stored position, then TRG nodes replace their coincident bank instance (they carry authored rotation) or append re-instances (revised 2026-07-20; v1.3.2's TRG-only model under-populated every level). **Cross-game level-object parity** (2026-07-24): the placement pipeline covers the whole PS1 lineage via `MeshCompanionResolver.TryResolvePsxLevelCompanions` — Spider-Man `*_g.psx`, THPS1/THPS2 bare-stem levels (recognized by a sibling `*_o.psx`+`*_t.trg`; their v2.0 TRG PLATFORM nodes are verified coincident with the bank at div 2.25, THPS1 24/30 & THPS2 12/17 refs at δ≈0), and Apocalypse chunked levels (`*_obj.psx`/`*obj.psx` bank attached to ONE primary — bare `<base>.psx` if present, else the first chunk `_1`/`_1a` — so a batch convert doesn't place the shared bank per chunk). All three families get the full bank + PLATFORM-overlay + POWERUP-pickup stack (Apocalypse's PLATFORM refs are mostly re-instances of authored BADDY/PLATFORM spawns rather than bank-coincident, but they stay in-bounds at the same div-2.25 node scale; the per-game `PsxLevelCompanions.ApplyTriggerOverlay` knob is retained to gate any build whose overlay later proves unfaithful). **Two-player/HORSE regions take the bank their TRG BOOT SCRIPT names** (`PsxTrgBootScript`, 2026-08-04, replacing a filename guess): `Trig_InitialParseTRGFile` (TRIG.cpp:2800, perfect 130/130) runs AUTOEXEC2 (node type 15) **INSTEAD of** AUTOEXEC (type 4) when two players are active — the scripts replace each other, not stack — and the bank is the last `0x8E SetObjFile` that script executes, stored in `pCurrentObjFile`, the only thing PLATFORM/CBackground instancing resolves against. A boot script naming none means the region genuinely has NO bank (a RESTART node never names one; its `0x80 SpoolEnv` names the GEOMETRY region, which is easy to conflate). HORSE is two-player — `LaunchTheDamnGame` sets `GNumberOfPlayers = 2` for every mode but 1-3 and HORSE is `GGame == 7`, hence the binary's many `GNumberOfPlayers == 2 && GGame != 7` guards — which **falsifies the previous claim that HORSE runs the one-player bank**. 13 of 47 variants change: `skdown_2`/`_h`, `skbul_2`, `skmar_2`, `skven_2` drop the bank they never load (the reported over-placement) and `skros_h` retargets `SkRos_O` → `SkRosO2`; reading the TRG also spells banks exactly, retiring the `_o2`-vs-`o2` table. Apocalypse geometry chunks (`city_2`, `grav_2`…) are spelled like variants and share a `_t.trg` that DOES name a bank, so they are excluded explicitly or the shared bank attaches to every chunk. Report: `tools/diagnostics/psx_variant_bank_report.py`. **TRG POWERUP pickups** (`PsxPowerupPlacementResolver`, 2026-07-23; THPS + Apocalypse added 2026-07-24): POWERUP nodes (type 5) carry a numeric `pickupType` the engine's `CPowerUp` ctor stores as `mType` and switches to an items.psx mesh (`InitItem("items")` then `Spool_GetModel(hash)`; `Trig_CreateObject` passes the node subtype straight in, so TRG pickupType == mType). Semi-trans lifts move along POSITION-AVERAGED directions built per FILE in authored-world space (per-face directions physically tore the all-ST webdome open at every shared edge, and a per-mesh map left horizontal cracks at webdome3/firedome's per-ring object boundaries), and meshes without per-vertex normals get 60°-thresholded position-welded normals (`PsxNormalWelder` — the SKBUL sky dome's 32 texture-band primitives each shaded as their own facet island). **Engine-lit faces** (`IsEngineLitFace`): RE'd properly 2026-08-02 against the matched THPS2 decomp plus byte-level signature matching, correcting the earlier "authored albedo × lit(N)" claim, which is WRONG. `M3d_Render` takes the dynamic path when `(pModel->Flags & 4) || (pItem->Flags & 0x80)` — and the PS1 loader ORs each face's word0 into `SModel.Flags`, so the model bit just means "any face is lit" and the real selection is PER FACE in ProcessPolys. It then calls `M3dAsm_GetDynamicLighting` over the model's NORMALS, which writes **0x00FFFFFF (white) into the GTE RGB register once, outside its loop**, and runs `NCCS` per normal. NCCS multiplies by that register, so with white it is a no-op: **the shaded colour is the light alone and the authored vertex colours are never read** for a lit face. The identical instruction sequence appears exactly once in all NINE PS1-era binaries (Apocalypse, THPS1 ×2, THPS2 ×2, Spider-Man ×2, SM2:EE ×3; Spider-Man final @0x8007BFE4), so it is engine-wide. The light is per-ITEM (`pItem->mpLight`), which is why no file-level signal can identify it: ordinary items get `M3d_DefaultLight` (OB.cpp:233), the skater gets `Skater_DefaultLight` (MECH.cpp:629), and the front end substitutes its own (PLAYERSELECT/CREATE). `M3d_DefaultLight` is byte-identical in THPS2 and Spider-Man (found at 0x800A6214 in spiderman_final without symbols) — a HEMISPHERE rig, dirs (0,+1,0)/(0,-1,0)/(0,0,+1) with colour rows R(1.000,0.5625,0.500) G(0.500,0.8125,0.500) B(0.125,1.000,0.500) and ambient 0.125; PS1 is Y-DOWN, so the cool row lights upward-facing surfaces. `Skater_DefaultLight` is mono grey (0.156/0.719/0.078, ambient 0.531) — these are the constants this codebase previously mislabelled as a "front-end preview light"; they are neither front-end nor a preview. `PsxEngineLight.Evaluate` reproduces one NCCS (`ambient + ColorMatrix × max(0, LightMatrix·N)`, clamped) and `BakeEngineLight` applies it per lit face corner, scaled 255/128 into the textured modulation domain because a fully lit textured surface DOUBLES the texel rather than landing on neutral. Scanner: `tools/diagnostics/psx_light_table_scan.py`; disassembly via `tools/diagnostics/psx_disasm.py`. **Scope**: dynamic lighting is a CHARACTER/PROP feature only — a corpus lit-census finds **zero** lit faces in any level geometry (`_g`) file, 117 of 3,113 across six `_o` banks, and 224,221 of 241,069 across 401 character/prop files. Levels are entirely pre-lit with authored vertex colours, which is why they render correctly with no rig at all. **The rig is NEVER inferred**: the file records which faces the engine lights but never which light (`mpLight` is assigned only by game code — `OB.cpp` item default, `MECH.cpp` skater, `PLAYERSELECT`/`CREATE` front end), and TRG node type 501 is a `CWobblyGlow` lamp effect, not a shading light (`CBody::DoLightingSetup` is an empty `jr $ra`). So `PsxEngineLight.Presets` exposes only the rigs the decomp NAMES — `item-default`, `skater`, `skater-mars` — selected by the caller via `mesh --psx-light <name>`; omitted, lit faces keep authored colours for the viewer to light. Spider-Man's rig set was traced 2026-08-03 with no symbols (`tools/diagnostics/psx_xref_scan.py`): the binary holds exactly TWO stores of a light into `mpLight` (offset 0x38) — the item ctor @0x80058D90 assigning `M3d_DefaultLight` (0x800A6214), and @0x80048214 assigning **0x80098F1C**, whose ctor (entry 0x80047DF8) is called from two sites each allocating a 0x1020-byte object, the game's largest entity — the structural analogue of THPS2's CBruce, hence the `spiderman-player` preset. Full stack RE'd 2026-08-05 (`Core/Formats/N64/`). **ERZ compression** (`ErzDecoder`): block = `"ERZ"+ver(u8) + u16 1 + u16 0 + u32 BE decompSize + u32 BE compSize + 6 bytes + bitstream at +18`; TWO unrelated codecs — v2 (boot packages, 64KB units): LZ with MSB-first low-bit-sentinel bit buffer, interleaved byte literals, aligned raw runs, RLE fill, 16-bit swapped extended distances; v1 (asset corpora, 16KB units): Deflate-like coder — three per-block canonical code tables (5-bit count + 4-bit lengths, bit-reversed codes, gamma-style values), LSB-first 16-bit LE window, byte-aligned literal runs with window re-sync, 16-bit match-count prefix; v1 READS AHEAD past compressedSize (reads past the block zero-fill; bits never reach output). Both are mechanical transcriptions of the ROMs' own MIPS decompressors, validated against emulator goldens (`tools/diagnostics/erz_emu_decode.py` executes the ROM code under a minimal MIPS interpreter; SHA-256-pinned in `ErzDecoderTests`). **Container** (`N64RomArchive`): the BE u32 immediately BEFORE the boot table is a KSEG1 pointer (`0xB0......` & 0x0FFFFFFF) to a MASTER DIRECTORY — a root table of stream-group directories (THPS1 7, THPS2/THPS3 9, Spider-Man 8; standard table shape = BE count + count+1 NON-DECREASING offsets, equal neighbours = authored empty slots, offs[0] == 4+4*(count+1), root tolerates pad). A compressed group is ONE logical stream cut into 16KB ERZ units for random access (block = decompressedOffset >> 14); uncompressed groups are raw audio (wavetables + 'N64 PtrTablesV2' banks — no VAB anywhere; PS1 audio was not ported). Each record is the SAME recursive BE table grammar as the ROM directories, bottoming out in 3-child geometry groups `{12-byte descriptor, blob A, blob B}` where the descriptor is `[u32 id][u16][u16 kind][u32 per-game constant]` and blob B is `{u32 n; u32 entries[n]}`. **The constant is PER GAME, not universal** (measured 2026-08-06 over every record): THPS1 0x00FB7A00 (18,456 groups), THPS2 0x00016B00 (25,754), THPS3 0x00016B00 (22,577), Spider-Man 0x00262110 (15,817) — the earlier "0x00262110-prefixed" description generalized Spider-Man's value to all four. **Blob A is NOT a bit-packed vertex codec** — RE'd 2026-08-06, it is a PACKED F3DEX2 DISPLAY LIST over a plain vertex array, and it carries no coordinates at all. Node child [2] is the vertex POOL (`u32 count, u32 0`, then count x 16-byte stock F3DEX2 `Vtx`: `s16 x,y,z; u16 flag(always 0); s16 s,t; u8 r,g,b,a`), stored BYTE-PLANE TRANSPOSED (16 planes of `count` bytes) in THPS2/THPS3/Spider-Man but PLAIN in THPS1 — assuming one universal layout silently garbles a whole ROM, so `N64RenderBankFile` decides per node by testing both against that node's own float bounds. Blob A is a 2-byte token stream: `0x00` G_ENDDL; `&0x80` triangle (`w=(b<<8)|next`, corners `w&31`, `(w>>5)&31`, `(w>>10)&31` — that order matches the PS1 sibling exactly, the GBI word the engine emits is its reverse); `&0xE0==0x20` G_VTX (`n=w&31` with 0 meaning 32, `v0=(w>>5)&31`, source = a pool cursor advancing across the whole node); `&0xE0==0x40` G_MTX (matrix index = next byte); `&0xE0==0x60` G_MODIFYVTX ST override (5 bytes, BE s16 s/t); then zero-pad to a multiple of 4. Blob B holds one u32 per triangle whose LOW half is the PS1 per-face flag word (100% agreement under position-aligned join). Vertices are in MODEL space — the G_MTX index selects a runtime animation matrix, NOT an authored placement offset (measured: applying object-table offsets scatters the model). Positions are `trunc(PS1raw / k)`, k=8 for super/animated models and k=1 otherwise (inferred from the shell's super flag; 45/46 correct, `sk2def` is the known exception, no field carrying k has been found). ST is S10.5 texels. `kind & 0x8000` marks a second, non-display-list class (2,071 groups, 2.5%) that is skipped. The display-list emitter reduces it to a per-draw-entry boolean `((desc[+4] >> 10) & 1) ^ 1` (THPS2 @0x800C5F28, THPS3 @0x800CA768, SM @0x800CFC18) and the consumer emits G_GEOMETRYMODE (0xD9) with set-mask 0x00020000 when true; THPS1's older emitter tests the raw word in place @0x800AA2F4 with the same polarity. - **VID1 video**: THAW GameCube movie container (`VID1`+`HEAD`/`VIDH` chunks, MPEG-4-derived codec ported from the GC binary) → MP4 via pure C# decode piped to ffmpeg. Header: 512×384 @ 29.97 fps (num 2997 / den 100 at VIDH+8+0x10). All 8 corpus files convert (8/8). **In-app playback** streams through `Vid1MediaSource`: a dedicated worker thread decodes ahead into a bounded frame queue and sample requests take deferrals when they outrun it (the old synchronous design froze on decode stalls and ended the stream on any mid-stream hiccup — "some don't play"); seeks reposition on the worker (forward = fast-forward decode, backward = restart — VID1 has no random access) with newer scrubs superseding older ones, and mid-stream decode failures hold the last good frame instead of ending playback. **Seeking is anchor-based** (`Vid1SeekAnchorIndex` + `Vid1ReferenceSnapshot`): reference-state snapshots (~1 MB: both plane sets + MB-state mirrors + state words — exactly the `Vid1Decoder.Reset` field set) are captured every N emissions with adaptive spacing (cap 40 anchors, stride doubles when full), seeks resume from max(current position, best anchor, nearest PreambleClass-0 intra frame) and fast-forward with plane-only decodes (no BGRA conversion); the held presentation frame's BGRA regenerates from the reference planes (the held frame is always the last promoted reference — B-frames never promote). Byte-identical to linear decode (`Vid1SeekTests`). **Startup is stutter-hardened** (2026-07-16): a fresh Start-at-0 no longer resets the already-warm decode queue (`Vid1StartupSeekPolicy.IsRedundantStartAtZero`, headlessly unit-tested), the Starting request holds a deferral until ~6 frames are queued (500 ms timeout so short/broken files still start; deliberately NOT `BufferTime` — pipeline-buffering uncompressed BGRA taxes every seek), and the first ~1 MB anchor capture waits until emission ordinal 90 (~3 s) instead of 30.
- **Video tab** (GUI): Unified Video Conversion tab handles SFD/PSS/BIK (ffmpeg), STR, and VID1 with playback preview via MediaPlayerElement. Recursive folder scans (header-sniffed: SFD/PSS gate on the MPEG-PS pack header), per-file convert checkboxes (+check-all master), zoom (fit/100%+pan), and a persistent on-disk preview cache keyed by path+size+mtime (preview conversions use `-preset ultrafast`; all ffmpeg MP4 outputs now carry `-movflags +faststart -pix_fmt yuv420p`).
- **Unpack tab** (GUI + CLI): Recursive extraction of all game archives in a directory. Multi-pass loop: scans for archives → extracts → rescans for nested archives (e.g. WAD containing PRE) → repeats until no new archives found. Supports WAD, PRE, compressed PRE (PRE3/PRX/PRD/PRF/PRG), PKR, DDX, BON, PAK, QTex ZIP, CUT, and disc images (ISO/CUE/GDI/IMG+CCD — a disc extracts into `{stem}/`, then its WADs/PAKs recurse). Already-extracted detection (skips if `{stem}/` directory exists and is non-empty). GUI: folder picker, archive list with status/progress, cancel support. CLI: `unpack <input-dir> [-v]`.

## glTF Validation

After converting meshes to .glb, **always validate the output** using the Khronos glTF validator. Download a release from <https://github.com/KhronosGroup/glTF-Validator/releases> and either drop the binary at `tools/gltf_validator_bin/gltf_validator.exe` (kept out of the repo via `.gitignore`) or invoke it from wherever it lives on your system.

```bash
# Validate a single file
tools/gltf_validator_bin/gltf_validator.exe <file.glb>

# Validate a directory (recursive)
tools/gltf_validator_bin/gltf_validator.exe <directory>

# JSON report to stdout (parse with Python for material/texture/mesh counts)
tools/gltf_validator_bin/gltf_validator.exe -o <file.glb>
```

Key things to check: 0 errors, 0 warnings. `UNUSED_OBJECT` infos on `TEXCOORD_0` indicate meshes with UV coordinates but no texture assigned to the material — expected for untextured geometry, but a bug if textures should be present.

For quick programmatic checks, parse the GLB JSON directly (first chunk after 12-byte header):
```python
import struct, json
with open('file.glb', 'rb') as f:
    f.read(12)  # skip magic/version/length
    clen, _ = struct.unpack('<II', f.read(8))
    d = json.loads(f.read(clen).decode().rstrip('\x00'))
    print(f"Materials: {len(d.get('materials',[]))}, Textures: {len(d.get('textures',[]))}")
```

### Archive filesystem (`Core/Formats/ArchiveFs/`)

Archives are read through `IArchiveFileSystem` — a read-only filesystem over any WAD/PRE/PRE3/PKR/PAK/DDX/BON/ZIP/CUT container: lazily-indexed entries (`FindByPath` full-path case-insensitive with `\`↔`/` normalized, `FindByName` legacy flat first-wins, `FindAllByName` for directory disambiguation), **thread-safe per-entry reads** (`RandomAccess` on one `SafeFileHandle` — no whole-file buffering, so >2 GB WADs like Project 8's 2.78 GB DATAP.WAD open fine; the old `File.ReadAllBytes` backend rejected them), and **`TryOpenNested`** for archives-inside-archives (.pre/.prx/.prd/.prf/.prg/.pkr/.pak/.apk entries open in place with weak-ref'd buffers; nested PAKs auto-pair with sibling `.pab` entries in the same parent; depth cap 4). Detection lives in ONE place, `Archives/ArchiveTypeDetector.cs` (folded from the five previously duplicated extension/classification switches); `ArchiveFileSystem.TryOpen(path)` is the factory; `ArchiveAssetBackend` is a thin compatibility shim over it and `ArchiveAssetSource`/`AssetSource` remain the per-entry seam the converters consume. The per-entry `IsCompressed` flag is OVERLOADED per type (PAK = "has .pab companion", THUG WAD = NO_WAD external reference) — `ArchiveEntryDecoder` scopes real decompression to CompressedPre/PKR/ZIP only. Both GUI scanners walk nested archives breadth-first and probe entries with `Parallel.ForEach` + `IProgress` (THPS3's level `.bsp`/`.skn` inside SKATE3.WAD's PREs list directly; the Texture tab folder scan no longer freezes the UI on 10k-file trees). Parity/2GB/nesting tests: `tests/.../Core/Formats/ArchiveFs/` (unit `[Fact]`s + `[CorpusFact]` sweeps).

### Mesh extension routing (`Core/Formats/Mesh/Detection/`)

`MeshTypeDetector` is the single source of truth for "what kind of mesh is this?", the way `ArchiveTypeDetector` is for archives. It folded the five previously unsynchronized extension lists (`FormatProbeMesh`, `MeshCommand`, the GUI scanner's three gates, `MeshConverterTabScanAnalysis`, and the per-command filters) into one longest-match suffix table plus one content ladder, and owns the single stem rule (`GetStem`). Adding a mesh extension now means editing one table.

Bare `.skin`/`.mdl` need a content probe, and **the ladder order is load-bearing**: `XbxSceneFile.IsXbxScene` is nothing but a `(1,1,1)` version triple, which ~32% of PS2-build bare `.skin` files also satisfy, so it is tried LAST. (`MeshCommand.TryDetectAmbiguousScene` asked it FIRST and never called `IsThawPs2Skin` at all; copying that order would have misrouted ~700 PS2 skins.) The four PS2 predicates are mutually exclusive by construction — `IsPakMdl` and `IsPakSkin` each exclude the others — so their relative order does not matter. `.pak.ps2` is deliberately NOT a generic mesh candidate (`IsWorldzoneCandidate` is separate) because archive enumeration relies on non-candidate `.pak` entries falling through to nested-archive opening.

**Output paths**: game trees reuse asset names heavily — 1,678 bare `.col` share 287 stems (1,228 are literally `mission.col`), 4,974 `.skin.xbx` share 729 — so a flat `<output>/<stem>` silently overwrote all but the last. `MeshOutputPathPlanner` guarantees a bijection: unique stems keep the flat layout unchanged, colliding ones mirror their source directory, with a deterministic ordinal backstop. The disambiguated name applies to the EXPORT stem only — the import stem stays original because it is the companion-lookup key (`stem + ".ddx"/".lit"/"_o.ddm"/".ske.ps2"`).

**Cross-tree companions**: THPS4/THUG level `.geom.ps2` live under `Levels/<Stem>/` while their `.tex.ps2` dictionaries ship only inside the scene PRE at `pre/<Stem>Scn/Levels/<Stem>/` — `BuildTreeCompanionLocator` (opt-in via `MeshCompanionResolver.ReadTextureCompanion(searchBuildTree: true)`, enabled for the PS2 scene/geom call sites) resolves those by walking ≤4 ancestors to the build root on disk, or via `FindAllByName`/sibling `{stem}Scn.pre` nested opens for archive-backed sources. `AnimationDiscovery` similarly handles archive-backed characters (same-backend `Anims/` entries, preferring the character's stem-scoped subdir) and PSX characters' sibling animation-bank `.psx` files (anim-named + companion-library stems; previously manual Add-folder only).

## Deferred Items

### Not Game Formats / Not Archives

- **SCC**: Microsoft Visual SourceSafe `vssver.scc` version tracking files. Development artifacts accidentally shipped on disc. No game data.
- **BIN**: Generic file extension used for PS1 MIPS code overlays (game logic, menu screens), THPS2 data tables (cretex.bin, tricks.bin), and Dreamcast bootstrap executables. ~89% compiled machine code. Not suitable for asset extraction. See [spidey-decomp](https://github.com/krystalgamer/spidey-decomp) for Spider-Man module decompilation.
- **PAK raw data files**: 987 of 1,732 `.pak.ps2` files in THAW are raw data without entry tables (not extractable archives). Detected and gracefully skipped by `PakArchive.IsPakArchive()`.
- **PRK**: Custom park save data (8-20KB files named `custom1-20.prk`). Not archives.
- **PPV**: CLOSED — not Neversoft. The `.ppv`/`.zoo`/`.bfx` files under `WTC/SOUNDS` in `Spider-Man (2000-2-4, PSX - Prototype)` belong to Codemasters' TOCA World Touring Cars (the proto disc SCED_026.36 is a multi-game demo disc). No extraction work planned.

### Not Yet Implemented

- **THUG2 pre-compiled .skin.ps2 without .iskin.ps2 (bare conversions)**: 1,713 THUG2 pre-compiled skins route through `ThawPs2SkinFile` when no `.iskin.ps2` is available and convert to near-zero geometry (0-50 tris) — their VIF layout differs from THAW's. The 746 with non-THAW-conformant entry tables now REJECT at detection (owner-checksum gate) instead of replaying garbage; scans prefer co-located `.iskin.ps2` everywhere, so the GUI rarely hits this. A real THUG2-pre-compiled VIF decoder would be needed for the remainder (found 2026-07-15 during the 2g texture audit).
- **RW DFF / THPS3 animations**: No animation support yet. THPS3 likely uses RenderWare animation chunks or custom Neversoft formats. THPS4+ uses Neversoft SKA format (BonedAnim.cpp). Skinned DFF models currently export in bind pose (T-pose). SKA parsing itself works (rpHAnim variant, 928/929 parse) — the unresolved part is rotation/translation composition semantics (see `docs/thps3-ska-animation-correctness-handoff.md`).

### Research & Improvements

- **PowerVR format improvements**: DDS output with mip level preservation is implemented for formats 0x200 (twiddled+mip) and 0x400 (VQ+mip). Mip atlas PNG (`_mips.png`) output renders all mip levels into a single image for visual verification. GIMP PVR research: `Sample/gimp/plug-ins/common/file-pvr.c` supports additional format types (Small VQ, CLUT4/8, stride, etc.) but none of these appear in any Neversoft game files — scan of 20,726 textures across 1,041 files found zero unsupported format codes. Current six format types (0x100, 0x200, 0x300, 0x400, 0x900, 0xD00) provide complete coverage.
- **PSX mesh conversion**: Parser (`Core/Formats/Mesh/Psx/PsxMeshFile.cs`), glTF export via the unified pipeline (`Core/Formats/Mesh/Conversion/GltfModelExporter.cs` + `PsxGeometryWriter.cs`/`PsxSkinnedGeometryWriter.cs`), CLI (`CLI/PsxMeshCommand.cs`), and GUI tab (`App/Tabs/MeshConverterTab.xaml`). Level geometry (`_g.psx`) AND character models both work — re-verified 2026-07-07 with a five-build sweep (Apocalypse/THPS1/THPS2/Spider-Man/SM2EE): 490 character-class files converted with **zero real failures** (the only non-conversions are texture-only costume files correctly reporting "No mesh data"); Bruce (Apocalypse), Burnquist (THPS1), Hawk (THPS2), and Spidey render correct textured characters. The earlier "garbled character geometry" note predated the PSX animation-era mesh fixes and is obsolete. Remaining PS1-era gaps are animation-side (see `memory/psx_anim_status.md`), not static meshes. NxTools' `psx/import_psx.py` remains a useful cross-reference (skinned ÷16 scaling, HIER hierarchy, face stitching).
