# Neversoft Multitool - AI Assistant Instructions

## Project Overview

.NET 10.0 application for extracting and converting assets from Neversoft game files (PS1, Dreamcast, Xbox, PC). Features WinUI 3 GUI (Windows) and cross-platform CLI. Ported from Python/PyQt6.

Supported formats:

- **PS2/Xbox CAS polygon-removal metadata**: explicitly typed `.cas.ps2` and `.cas.xbx`/Windows sidecars use a strict little-endian version-2 layout and are inspection-only through the `cas` CLI. Schema-v1 JSON preserves header masks, PS2 vertex references, Xbox packed words plus their proven mesh-load-order/three-index derivation, exact source size/hash, and `geometryApplicationStatus: "notApplied"`. Parsing requires exact EOF and never infers a dialect from bare `.cas`; `.cas.ngc` is a distinct unsupported envelope. CUT extraction now gives CAS members the container suffix (`.cas.ps2`/`.cas.xbx`, with bare `.cut` remaining `.cas`) so supported members route without content guessing. The retained loose corpus pins 13,076 files / 189,909 entries, and 1,058 typed CUT members / 59,188 entries parse under the same strict layouts. Applying removal records to geometry remains unresolved because the runtime mesh-binding contract is not yet proven.

- **Compiled PS2/Xbox WGT cutscene-head scaling metadata**: explicitly typed `.wgt.ps2` and `.wgt.xbx`/Windows files are accepted only as the source-proven little-endian version-1 layout: `{i32 version=1, i32 vertexCount}`, then `3×N` raw float weights and `3×N` signed-byte bone indices, with exact EOF at `8+15×N` and finite weights required. `wgt` emits deterministic schema-v1 inspection JSON with full source size/hash and `geometryApplicationStatus: "notApplied"`; CUT extraction preserves the container suffix on WGT members. The loose oracle pins 12 physical files / 14,602 vertices / eight unique payloads, and 212 v1 CUT members / 266,356 vertices all SHA-match those loose payloads. Bare authoring `.wgt` (`4+24×N`), THUG2 PS2 version 2 (`8+19×N`), and `.wgt.ngc` remain rejected. Applying WGT to geometry still requires the selected profile's bone scales and an authoritative companion-mesh vertex-order binding.

- **PSX files**: Multi-purpose format containing textures + optional 3D mesh geometry. File naming conventions: `*_g.psx` = level geometry, `*_l.psx` = texture library (paired with `_g`), `*_o.psx` = level objects, no suffix = character/creature/item model. Textures: 4-bit/8-bit paletted (PS1), 16-bit PowerVR (twiddled, VQ, rectangle) — PS1, Dreamcast, Xbox. Meshes: → glTF (.glb) with vertex colors, normals, and texture references. **`_o.psx` object banks are placed layers**: the bank's object-table positions are authored world instances (same convention as DDM/PSX layout placement), and companion TRG PLATFORM nodes (subtype 0x192, model-checksum opcode 0x212F) only OVERLAY scripted re-instances — corpus-proven by the historical `psx_level_object_survey` analysis (now pinned by C# tests) (TRG checksums reference a fraction of every bank: final l2a2 4/63, l4a1 0/19; coincident node/bank positions match exactly). `Core/Formats/Mesh/Conversion/PsxLevelObjectPlacementResolver.cs` seeds every bank object at its stored position, then TRG nodes replace their coincident bank instance (they carry authored rotation) or append re-instances (revised 2026-07-20; v1.3.2's TRG-only model under-populated every level). **Cross-game level-object parity** (2026-07-24): the placement pipeline covers the whole PS1 lineage via `MeshCompanionResolver.TryResolvePsxLevelCompanions` — Spider-Man `*_g.psx`, THPS1/THPS2 bare-stem levels (recognized by a sibling `*_o.psx`+`*_t.trg`; their v2.0 TRG PLATFORM nodes are verified coincident with the bank at div 2.25, THPS1 24/30 & THPS2 12/17 refs at δ≈0), and Apocalypse chunked levels (`*_obj.psx`/`*obj.psx` bank attached to ONE primary — bare `<base>.psx` if present, else the first chunk `_1`/`_1a` — so a batch convert doesn't place the shared bank per chunk). All three families get the full bank + PLATFORM-overlay + POWERUP-pickup stack (Apocalypse's PLATFORM refs are mostly re-instances of authored BADDY/PLATFORM spawns rather than bank-coincident, but they stay in-bounds at the same div-2.25 node scale; the per-game `PsxLevelCompanions.ApplyTriggerOverlay` knob is retained to gate any build whose overlay later proves unfaithful). **Two-player/HORSE regions take the bank their TRG BOOT SCRIPT names** (`PsxTrgBootScript`, 2026-08-04, replacing a filename guess): `Trig_InitialParseTRGFile` (TRIG.cpp:2800, perfect 130/130) runs AUTOEXEC2 (node type 15) **INSTEAD of** AUTOEXEC (type 4) when two players are active — the scripts replace each other, not stack — and the bank is the last `0x8E SetObjFile` that script executes, stored in `pCurrentObjFile`, the only thing PLATFORM/CBackground instancing resolves against. A compressed group is ONE logical stream cut into 16KB ERZ units for random access (block = decompressedOffset >> 14); uncompressed groups are raw audio (wavetables + 'N64 PtrTablesV2' banks — no VAB anywhere; PS1 audio was not ported). The tree covers every block incl. odd-offset ones an aligned scan misses (flat scan retained as fallback for unknown ROMs). **Carving** (`N64AssetCarver`): reassembled streams open with recursive payload tables (offs[0] may be +4: align-8 pad / trailing zero u32); entries classify structurally → typed platform-suffixed outputs, validated against the PS1 corpora of the same games: `models/NNN/NNN_<name>.psx.n64` (4-slot bundles, the geometry file carrying its bundle slot in the NAME as well as the directory so a file list can tell 594 of them apart, plus the PS1 name its CONTENT resolves to — see **Bundle names** below: PSX object table byte-identical to PS1 after u32 swap + bounds + u32-byteswapped TEXTURE-STRIPPED PSX v4 shell + u32 render-bank link; PS1-format kept for CPU skinning), `triggers/*.trg.n64` ('GRT_' = '_TRG' swapped, v2.0/2.1, sizes match PS1 `*_t.trg`), `textures/<name>.tex.n64` (records named `psxtxt_<8-hex>` where the hex IS the PS1 opaque texture identifier — direct cross-platform join key — or real art names), `images/*.img.n64` (3-part CI records, 28B header magic 0x00080410), `sfx/*.sfx.n64` (PS1 cue grammar per-field BE, validated record-by-record — render-bank tails otherwise false-positive), `misc/` (`.rec` demo replays BYTE-IDENTICAL to the PS1 discs — little-endian data consumed by ported code; `.psh` #ifndef part-name headers named from their guards; gap/goal tables), `audiobanks/`, `audio/` (raw), `boot.bin` (MIPS BE code+data with the PS1 filename tables), and `group2/` = the N64-native render-geometry bank (per-model, linked from bundle slot 3 — `renderbank-id.bin` is a BE u32 index into group2's slot numbering, total and injective across all 594 bundles in the four ROMs, with ~20 leading records per ROM referenced by no bundle). Each record is the SAME recursive BE table grammar as the ROM directories, bottoming out in 3-child geometry groups `{12-byte descriptor, blob A, blob B}` where the descriptor is `[u32 id][u16][u16 kind][u32 per-game constant]` and blob B is `{u32 n; u32 entries[n]}`. **The constant is PER GAME, not universal** (measured 2026-08-06 over every record): THPS1 0x00FB7A00 (18,456 groups), THPS2 0x00016B00 (25,754), THPS3 0x00016B00 (22,577), Spider-Man 0x00262110 (15,817) — the earlier "0x00262110-prefixed" description generalized Spider-Man's value to all four. **Blob A is NOT a bit-packed vertex codec** — RE'd 2026-08-06, it is a PACKED F3DEX2 DISPLAY LIST over a plain vertex array, and it carries no coordinates at all. Node child [2] is the vertex POOL (`u32 count, u32 0`, then count x 16-byte stock F3DEX2 `Vtx`: `s16 x,y,z; u16 flag(always 0); s16 s,t; u8 r,g,b,a`), stored BYTE-PLANE TRANSPOSED (16 planes of `count` bytes) in THPS2/THPS3/Spider-Man but PLAIN in THPS1 — assuming one universal layout silently garbles a whole ROM, so `N64RenderBankFile` decides per node by testing both against that node's own float bounds. Blob A is a 2-byte token stream: `0x00` G_ENDDL; `&0x80` triangle (`w=(b<<8)|next`, corners `w&31`, `(w>>5)&31`, `(w>>10)&31` — that order matches the PS1 sibling exactly, the GBI word the engine emits is its reverse); `&0xE0==0x20` G_VTX (`n=w&31` with 0 meaning 32, `v0=(w>>5)&31`, source = a pool cursor advancing across the whole node); `&0xE0==0x40` G_MTX (matrix index = next byte); `&0xE0==0x60` G_MODIFYVTX ST override (5 bytes, BE s16 s/t); then zero-pad to a multiple of 4. Blob B holds one u32 per triangle whose LOW half is the PS1 per-face flag word (100% agreement under position-aligned join). Vertices are in MODEL space — the G_MTX index selects a runtime animation matrix, NOT an authored placement offset (measured: applying object-table offsets scatters the model). Positions are `trunc(PS1raw / k)`, with k owned by the selected binding plan: ordinary supers retain k=8, non-supers k=1, and only the exact Spider-Man `map` shell/render/id profile proves k=1 for a super. Scripts are LZSS-compressed blobs (same `LzssDecoder` as PRE v3) of the classic token stream — **always little-endian, even on GC** — extended with THAW-only tokens: 0x47 fast-if / 0x48 fast-else / 0x49 fast-case (u16 runtime skip operands; explicit endif tokens remain) and 0x4A inline struct (u16 LE length + pad-to-4 + serialized struct in FILE byte order with relative pointers). Struct items add a THAW-only inline-script type (info 0x0087SSSS new / 0xSSSS0F00 old, SSSS = raw script byte size). `QbSectionParser` synthesizes the equivalent raw token stream so the existing indexer/decompiler/GUI work unchanged. Sweep: **11,909/11,909 files (2,933 PS2 + 3,754 PC + 5,222 GC), 49,755 scripts + 37,658 globals, 0 failures.** THAW name resolution: **97.1% PS2 / 99.2% PC / 89.1% GC** via `QbKeyNames.ThawDbg.txt` — 137,054 checksum→name pairs harvested from the `[Checksums]` sections of the shipped debug archives (`DATAP/pak/dbg.pak.ps2` + PC `dbg.pak.wpc`) by the original `harvest_thaw_dbg_names` run (now preserved by the tracked resource and tests). Reference: Nanook/Queen-Bee `QueenBeeParser/Qb` (`Sample/queen-bee`); diagnostics: the historical `thaw_qb_probe` analysis (now pinned by C# tests). Name resolution: 3-tier (file-local CHECKSUM_NAME → global QbKey dictionary (~424,800 entries across the `QbKeyNames*.txt` embedded resources) → `#"0xHHHHHHHH"` fallback). Decompiler reconstructs indentation for script/endscript, if/else/endif, begin/repeat, switch/case/endswitch, struct/array nesting. CLI: `qb <input> [-o output] [-v]`. GUI: integrated in Script Decompiler tab.
- **SFD video**: CRI Sofdec video (Dreamcast) → MP4 via ffmpeg. MPEG-PS container with MPEG-1 video + ADX audio. Requires ffmpeg on PATH.
- **STR video**: PS1 MDEC video streams → MP4 via pure C# decoder + ffmpeg encoding. 2336-byte CD-ROM sectors with interleaved XA-ADPCM audio. Variable resolutions (320×240, 320×192, 96×64). Present in Apocalypse, Spider-Man, THPS1/2 (PS1). Audio extracted via XaDecoder, raw RGB24 frames piped to ffmpeg stdin.
- **VID1 video**: THAW GameCube movie container (`VID1`+`HEAD`/`VIDH` chunks, MPEG-4-derived codec ported from the GC binary) → MP4 via pure C# decode piped to ffmpeg. Header: 512×384 @ 29.97 fps (num 2997 / den 100 at VIDH+8+0x10). All 8 corpus files convert (8/8). **In-app playback** streams through `Vid1MediaSource`: a dedicated worker thread decodes ahead into a bounded frame queue and sample requests take deferrals when they outrun it (the old synchronous design froze on decode stalls and ended the stream on any mid-stream hiccup — "some don't play"); seeks reposition on the worker (forward = fast-forward decode, backward = restart — VID1 has no random access) with newer scrubs superseding older ones, and mid-stream decode failures hold the last good frame instead of ending playback. **Seeking is anchor-based** (`Vid1SeekAnchorIndex` + `Vid1ReferenceSnapshot`): reference-state snapshots (~1 MB: both plane sets + MB-state mirrors + state words — exactly the `Vid1Decoder.Reset` field set) are captured every N emissions with adaptive spacing (cap 40 anchors, stride doubles when full), seeks resume from max(current position, best anchor, nearest PreambleClass-0 intra frame) and fast-forward with plane-only decodes (no BGRA conversion); the held presentation frame's BGRA regenerates from the reference planes (the held frame is always the last promoted reference — B-frames never promote). Byte-identical to linear decode (`Vid1SeekTests`). **Startup is stutter-hardened** (2026-07-16): a fresh Start-at-0 no longer resets the already-warm decode queue (`Vid1StartupSeekPolicy.IsRedundantStartAtZero`, headlessly unit-tested), the Starting request holds a deferral until ~6 frames are queued (500 ms timeout so short/broken files still start; deliberately NOT `BufferTime` — pipeline-buffering uncompressed BGRA taxes every seek), and the first ~1 MB anchor capture waits until emission ordinal 90 (~3 s) instead of 30.
- **Video tab** (GUI): Unified Video Conversion tab handles SFD/PSS/BIK (ffmpeg), STR, and VID1 with playback preview via MediaPlayerElement. Recursive folder scans (header-sniffed: SFD/PSS gate on the MPEG-PS pack header), per-file convert checkboxes (+check-all master), zoom (fit/100%+pan), and a persistent on-disk preview cache keyed by path+size+mtime (preview conversions use `-preset ultrafast`; all ffmpeg MP4 outputs now carry `-movflags +faststart -pix_fmt yuv420p`).
- **Unpack tab** (GUI + CLI): Recursive extraction of all game archives in a directory. Multi-pass loop: scans for archives → extracts → rescans for nested archives (e.g. WAD containing PRE) → repeats until no new archives found. Supports WAD, PRE, compressed PRE (PRE3/PRX/PRD/PRF/PRG), PKR, DDX, BON, PAK, QTex ZIP, CUT, and disc images (ISO/CUE/GDI/IMG+CCD — a disc extracts into `{stem}/`, then its WADs/PAKs recurse). Already-extracted detection (skips if `{stem}/` directory exists and is non-empty). GUI: folder picker, archive list with status/progress, cancel support. CLI: `unpack <input-dir> [-v]`.

## glTF Validation

After converting meshes to .glb, **always validate the output** using the Khronos glTF validator. Download the version described in `tools/vendor/gltf-validator/README.md` and place the binary at `tools/vendor/gltf-validator/gltf_validator.exe` (kept out of Git), or invoke it from wherever it lives on your system.

```bash
# Validate a single file
tools/vendor/gltf-validator/gltf_validator.exe <file.glb>

# Validate a directory (recursive)
tools/vendor/gltf-validator/gltf_validator.exe <directory>

# JSON report to stdout (parse with Python for material/texture/mesh counts)
tools/vendor/gltf-validator/gltf_validator.exe -o <file.glb>
```

Key things to check: 0 errors, 0 warnings. `UNUSED_OBJECT` infos on `TEXCOORD_0` indicate meshes with UV coordinates but no texture assigned to the material — expected for untextured geometry, but a bug if textures should be present.

For quick programmatic checks, parse the GLB JSON directly (first chunk after 12-byte header):
```python
import struct, json
with open('file.glb', 'rb') as f:
    f.read(12)  # skip magic/version/length
    clen, _ = struct.unpack('<II', f.read(8))
    d = json.loads(f.read(clen).decode().rstrip('\x00'))
    print(f"Materials: {len(d.get('materials',[]))}, Textures: {len(d.get('textures',[]))}")
```

## Reproducing a reported view (`glb-render --camera-* / --probe`)

When a level looks wrong in the app, press **P** in the Mesh tab's viewer and paste the clipboard line after `glb-render <file.glb>`. `Core/Rendering/GlbRenderer.cs` has two projection paths: the historical orthographic fit-to-bounds one (`ApplyViewRotation`, `--azimuth`/`--elevation`, unchanged and byte-identical when no camera is given) and, when `--camera-eye` is present, an explicit perspective camera (`PerspectiveProjector`) with **mandatory near-plane clipping** — a first-person level view always has geometry behind the eye, and an unclipped corner at depth ≤ 0 projects mirrored and smears across the frame. Depth is stored as `1/distance`: larger when nearer, which is what `SoftwareRasterizer`'s `z > depthBuffer` test already wanted, and the only quantity that interpolates linearly in screen space under perspective. Attribute interpolation stays affine (the PS1 warp), deliberately.

`--probe` (optionally `--probe-at=X,Y`) casts the centre ray and lists **every** surface along it — distance, the gap from the previous hit, node/mesh name, submesh + triangle index, alpha mode, facing, and any `__overlay<N>` / `__ghost` / `sky__` tag. Two hits a fraction of a unit apart *is* a z-fighting diagnosis, printed. `RenderSubmesh` carries `NodeName`/`MeshName` purely for this; node names are null in older exports and it falls back to the mesh name.

**What this image is and is not.** The software rasterizer reproduces **geometry, depth and framing**. It has no PS1 GPU emulation, sky pass, UV wibbles, colour pulses, billboards or alpha blending, and uses a fixed hemisphere light — so a semi-transparent pane in front of the subject alpha-*tests* rather than blends and can read as an occluder that the app draws through. Settle ordering questions with it; settle appearance questions in the app.

### Archive filesystem (`Core/Formats/ArchiveFs/`)

Archives are read through `IArchiveFileSystem` — a read-only filesystem over any WAD/PRE/PRE3/PKR/PAK/DDX/BON/ZIP/CUT container: lazily-indexed entries (`FindByPath` full-path case-insensitive with `\`↔`/` normalized, `FindByName` legacy flat first-wins, `FindAllByName` for directory disambiguation), **thread-safe per-entry reads** (`RandomAccess` on one `SafeFileHandle` — no whole-file buffering, so >2 GB WADs like Project 8's 2.78 GB DATAP.WAD open fine; the old `File.ReadAllBytes` backend rejected them), and **`TryOpenNested`** for archives-inside-archives (.pre/.prx/.prd/.prf/.prg/.pkr/.pak/.apk entries open in place with weak-ref'd buffers; nested PAKs auto-pair with sibling `.pab` entries in the same parent; depth cap 4). Detection lives in ONE place, `Archives/ArchiveTypeDetector.cs` (folded from the five previously duplicated extension/classification switches); `ArchiveFileSystem.TryOpen(path)` is the factory; `ArchiveAssetBackend` is a thin compatibility shim over it and `ArchiveAssetSource`/`AssetSource` remain the per-entry seam the converters consume. The per-entry `IsCompressed` flag is OVERLOADED per type (PAK = "has .pab companion", THUG WAD = NO_WAD external reference) — `ArchiveEntryDecoder` scopes real decompression to CompressedPre/PKR/ZIP only. Both GUI scanners walk nested archives breadth-first and probe entries with `Parallel.ForEach` + `IProgress` (THPS3's level `.bsp`/`.skn` inside SKATE3.WAD's PREs list directly; the Texture tab folder scan no longer freezes the UI on 10k-file trees). Parity/2GB/nesting tests: `tests/.../Core/Formats/ArchiveFs/` (unit `[Fact]`s + `[CorpusFact]` sweeps).

### Mesh extension routing (`Core/Formats/Mesh/Detection/`)

`MeshTypeDetector` is the single source of truth for "what kind of mesh is this?", the way `ArchiveTypeDetector` is for archives. It folded the five previously unsynchronized extension lists (`FormatProbeMesh`, `MeshCommand`, the GUI scanner's three gates, `MeshConverterTabScanAnalysis`, and the per-command filters) into one longest-match suffix table plus one content ladder, and owns the single stem rule (`GetStem`). Adding a mesh extension now means editing one table.

Bare `.skin`/`.mdl` need a content probe, and **the ladder order is load-bearing**: `XbxSceneFile.IsXbxScene` is nothing but a `(1,1,1)` version triple, which ~32% of PS2-build bare `.skin` files also satisfy, so it is tried LAST. (`MeshCommand.TryDetectAmbiguousScene` asked it FIRST and never called `IsThawPs2Skin` at all; copying that order would have misrouted ~700 PS2 skins.) The four PS2 predicates are mutually exclusive by construction — `IsPakMdl` and `IsPakSkin` each exclude the others — so their relative order does not matter. `.pak.ps2` is deliberately NOT a generic mesh candidate (`IsWorldzoneCandidate` is separate) because archive enumeration relies on non-candidate `.pak` entries falling through to nested-archive opening.

**Output paths**: game trees reuse asset names heavily — 1,678 bare `.col` share 287 stems (1,228 are literally `mission.col`), 4,974 `.skin.xbx` share 729 — so a flat `<output>/<stem>` silently overwrote all but the last. `MeshOutputPathPlanner` guarantees a bijection: unique stems keep the flat layout unchanged, colliding ones mirror their source directory, with a deterministic ordinal backstop. The disambiguated name applies to the EXPORT stem only — the import stem stays original because it is the companion-lookup key (`stem + ".ddx"/".lit"/"_o.ddm"/".ske.ps2"`).

**Cross-tree companions**: THPS4/THUG level `.geom.ps2` live under `Levels/<Stem>/` while their `.tex.ps2` dictionaries ship only inside the scene PRE at `pre/<Stem>Scn/Levels/<Stem>/` — `BuildTreeCompanionLocator` (opt-in via `MeshCompanionResolver.ReadTextureCompanion(searchBuildTree: true)`, enabled for the PS2 scene/geom call sites) resolves those by walking ≤4 ancestors to the build root on disk, or via `FindAllByName`/sibling `{stem}Scn.pre` nested opens for archive-backed sources. `AnimationDiscovery` similarly handles archive-backed characters (same-backend `Anims/` entries, preferring the character's stem-scoped subdir) and PSX characters' sibling animation-bank `.psx` files (anim-named + companion-library stems; previously manual Add-folder only).

## Deferred Items

### Not Game Formats / Not Archives

- **SCC**: Microsoft Visual SourceSafe `vssver.scc` version tracking files. Development artifacts accidentally shipped on disc. No game data.
- **BIN**: Generic file extension used for PS1 MIPS code overlays (game logic, menu screens), THPS2 data tables (cretex.bin, tricks.bin), and Dreamcast bootstrap executables. ~89% compiled machine code. Not suitable for asset extraction. See [spidey-decomp](https://github.com/krystalgamer/spidey-decomp) for Spider-Man module decompilation.
- **PAK raw data files**: 987 of 1,732 `.pak.ps2` files in THAW are raw data without entry tables (not extractable archives). Detected and gracefully skipped by `PakArchive.IsPakArchive()`.
- **PRK**: Custom park save data (8-20KB files named `custom1-20.prk`). Not archives.
- **PPV**: CLOSED — not Neversoft. The `.ppv`/`.zoo`/`.bfx` files under `WTC/SOUNDS` in `Spider-Man (2000-2-4, PSX - Prototype)` belong to Codemasters' TOCA World Touring Cars (the proto disc SCED_026.36 is a multi-game demo disc). No extraction work planned.

### In Progress (Not Yet Bug-Free)

- **Script Decompiler tab** (GUI): Unified tab (`App/Tabs/ScriptDecompilerTab.xaml`) handles both TRG trigger files and QB compiled scripts. TRG: file picker (.trg), node tree with type/position/command detail panels, JSON export. QB: file picker (.qb), item tree (SCRIPT/GLOBAL) with decompiled source detail panel, `.q` source text export. Directory scan finds both extensions with background parsing for metadata. Shared expandable list UI via `{Binding}` templates (supports polymorphic TrgFileEntry/QbFileEntry + TrgNodeEntry/QbItemEntry models).
- **QBKey name resolution**: all `QbKeyNames*.txt` embedded resources (~424,800 hash→name mappings total) are loaded at startup into a `FrozenDictionary` (first-wins, main file has priority). Format: `name=0xHASH` per line. `QbKeyNames.txt` (18,523): discovered via `qbkey cross-ref` matching DDM plaintext names against PSX QBKey hashes across 104 THPS2X Xbox file pairs, plus archive filename scanning — coverage: **mesh hashes 81.9% (19,336/23,611)**. `QbKeyNames.ThawDbg.txt` (137,054): harvested from THAW's shipped debug archives (`dbg.pak.ps2`/`dbg.pak.wpc` `[Checksums]` sections) once from those archives; the tracked resource and tests now preserve the result — it drives THAW script decompilation to 89-99% resolution. **`QbKeyNames.QbLocalNames.txt` (206,215) is the biggest single source**: inline `CHECKSUM_NAME` (token 0x2B) registrations harvested GLOBALLY from the THPS3/THPS4/THUG/THUG2 script corpus and validated by re-hash; the tracked resource and parser tests now preserve the result. The engine only ever used these file-locally (`QbFile.LocalNames`), so a name defined in one script did not resolve in another; aggregating the proven pairs gives those four games — which ship NO debug archives, unlike THAW/Project 8 — their primary cross-file resolution. THAW's own `CHECKSUM_NAME` pairs were stripped in retail (they don't re-hash), which is exactly why THAW needs the separate `dbg.pak`. `DiscNames`/`ScriptRefs`/`CutScenes`/`ThpgDbg` add proven pak-key/script-ref/cutscene/Project-8 names. Texture identifiers are build-tool-assigned IDs (not name hashes), so QbKey resolution does not apply to them — but THAW textures DO recover source-art names via a **separate** map, `Core/Formats/Texture/ThawTextureNames.cs` (+ `.txt`, 2,132 pairs): the compiled-texture checksum → original art name mined from the `debug.log` inside each QTex `.tex.zip` bundle; the tracked resource and texture tests preserve that harvest. It is deliberately kept OUT of `QbKeyNames*.txt` — those checksums are opaque build ids, not CRC(name), so mixing them in would poison every proven-name harvest's `existing_hashes()` and the coverage metric. Consumed by `ThawTexFile`/`NgcTexFile` naming (`ThawTextureNames.TryResolve(checksum) ?? QbKey.TryResolve(checksum)`).
  - **Hash algorithm**: PS1/DC/Xbox-era Neversoft games use **case-sensitive** reflected CRC-32 (polynomial 0xEDB88320, init 0xFFFFFFFF, no final XOR, **no lowercasing**). This was confirmed by verifying DDM checksum fields match case-sensitive CRC-32 of mixed-case mesh names (e.g. `Itm_Bonus01`). `QbKey.Hash()` is case-sensitive; `QbKey.HashLower()` provides the THUG+ era lowercase variant. The `io_thps_scene` Blender addon documents the same split: `crc32b_from_string()` (no lowercase) for THPS1/2 vs `crc_from_string()` (lowercase) for THUG+.
  - **Texture identifiers (NOT name hashes)**: The PSX "texture name" array stores opaque identifiers used as keys in `TextureChecksumHashTable` (a 512-bucket hash table, decompiled from THPS2 proto). `ProcessNewPSX` reads each identifier, looks it up via `Spool_FindTextureEntry__FUi`, then **replaces the value in-place with a pointer** to the texture entry struct. Values include small numbers like `0x0000001E` (30) that cannot be CRC-32 of any string, ruling out name hashing. Same identifier appears across files with different texture dimensions (e.g. `0x3FB86DC4`: hawk2.PSX 32x64 vs hawk2b.PSX 32x32), proving they're not pixel-data checksums either. The `TexId` field in the per-texture header is actually a **palette hash** (passed to `Pal_FindPaletteEntry__FUi`), not a texture name. These are build-tool-assigned identifiers; name resolution is not applicable. See `psx_decompiled.c` in the WSL decomp project (below) for the full decompilation.
  - `qbkey cross-ref <ddm-dir> <psx-dir>` — cross-reference DDM vs PSX hashes. `--export path.txt` merges discovered + existing mappings. `--scan-archives <builds-path>` scans WAD/PRE/BON/PKR/DDX archive filenames and hashes them against PSX pools.
  - `qbkey import <names-file> [--psx-dir <path>]` — import candidate names from external sources (e.g. C pipeline output), hash with QBKey, check against PSX hashes, optionally export merged dictionary.
  - External C pipeline tool in `tools/qbkey_pipeline/` provides `collect-names` (BON/DDX/DDM/PRE/PKR + executable string scraping), `match`, `brute`, and `brute-gpu` subcommands. Compile: `clang -O3 -D_CRT_SECURE_NO_WARNINGS -o qbkey_pipeline.exe qbkey_pipeline.c`. Add `-fopenmp` for multithreaded CPU brute-force. Add `-DHAS_OPENCL -DCL_TARGET_OPENCL_VERSION=120 -I"<CUDA>/include" -L"<CUDA>/lib/x64" -lOpenCL` for GPU brute-force.
  - **GHIDRA decompilation pipeline** (lives in the WSL decomp project at `\\wsl.localhost\Ubuntu\home\slfx77\thps2-psx-proto\`, not in this repo): decompiles PSX functions from the THPS2 PSX prototype (SLUS_900.86 + MAIN.SYM, 3,566 PSY-Q symbols). Only the THPS2 prototypes have SYM files; other builds require signature-based matching. This repository retains only input-agnostic helpers under `tools/reverse-engineering/ghidra/`, not generated Ghidra projects or build-specific phase outputs.
  - **GHIDRA headless string extraction**: `tools/reverse-engineering/ghidra/ExtractStrings.java` is a generic Java post-script that extracts analyzed strings from executables. Its output can feed `qbkey import <combined> --psx-dir <path>`. Requires Ghidra 11+ and Java 17+ with `GHIDRA_HOME` set.

### Research & Improvements

- **THUG2 precompiled `.skin.ps2` decoder is evidence-gated, not a shipped orphan gap**: 2,478 physical PS2 copies collapse to 739 unique payload hashes; all 739 canonical files have a same-stem `.iskin.ps2`, and the 1,739 apparent bare/preload copies are byte-identical to one of those paired assets. Scans already prefer `.iskin`, so every shipped unique model has a supported source. Keep the 746-entry non-THAW owner-checksum rejection; only revisit native precompiled VIF decoding with a genuinely unique orphan or an explicit detached-copy use case.

- **PowerVR format improvements**: DDS output with mip level preservation is implemented for formats 0x200 (twiddled+mip) and 0x400 (VQ+mip). Mip atlas PNG (`_mips.png`) output renders all mip levels into a single image for visual verification. GIMP PVR research: `Sample/gimp/plug-ins/common/file-pvr.c` supports additional format types (Small VQ, CLUT4/8, stride, etc.) but none of these appear in any Neversoft game files — scan of 20,726 textures across 1,041 files found zero unsupported format codes. Current six format types (0x100, 0x200, 0x300, 0x400, 0x900, 0xD00) provide complete coverage.
- **PSX mesh conversion**: Parser (`Core/Formats/Mesh/Psx/PsxMeshFile.cs`), glTF export via the unified pipeline (`Core/Formats/Mesh/Conversion/GltfModelExporter.cs` + `PsxGeometryWriter.cs`/`PsxSkinnedGeometryWriter.cs`), CLI (`CLI/PsxMeshCommand.cs`), and GUI tab (`App/Tabs/MeshConverterTab.xaml`). Level geometry (`_g.psx`) AND character models both work — re-verified 2026-07-07 with a five-build sweep (Apocalypse/THPS1/THPS2/Spider-Man/SM2EE): 490 character-class files converted with **zero real failures** (the only non-conversions are texture-only costume files correctly reporting "No mesh data"); Bruce (Apocalypse), Burnquist (THPS1), Hawk (THPS2), and Spidey render correct textured characters. The earlier "garbled character geometry" note predated the PSX animation-era mesh fixes and is obsolete. Remaining PS1-era gaps are animation-side (see `memory/psx_anim_status.md`), not static meshes. NxTools' `psx/import_psx.py` remains a useful cross-reference (skinned ÷16 scaling, HIER hierarchy, face stitching).
